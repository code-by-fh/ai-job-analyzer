### 4. Key Architectural Decisions (ADRs)

* **OpenRouter Config:** Stored in DB (`system_settings`), not in `.env` (dynamic model switches via UI).
* **Process Isolation:** Separate queue model (`ai_queue` vs. `scraper_queue`); Playwright crawls do not block AI tasks.
* **Single-Container Deployment:** All 4 backend processes via `supervisord` in a single Docker container.
* **Deferred Platform Creation:** Platform is only created upon completion of the setup wizard (no `pending_setup` overhead).
* **URL-Pattern Inference:** Character-wise common prefix (`os.path.commonprefix`) with trim to the last natural separator — more robust than a segment-wise approach for boards with IDs in the path.
* **Status Transition Table:** `server/core/job_status.py::ALLOWED_TRANSITIONS` is the single source for user status changes. It is permissive (backward moves and skips are allowed and always recorded in `job_status_history`). `SEEN`, `GENERATING` and `FAILED` can never be a target (400); `SEEN` and `GENERATING` cannot be left by hand (409); unknown legacy values may move to any user status. A status change on an archived job restores it. The web `domain/` mirror must match this table.
* **Archive Reason:** `jobs.archive_reason` (`THRESHOLD` | `USER`) separates "Unter Schwellwert" from "Von dir aussortiert". Any user restore sets `jobs.kept_by_user`, and threshold runs never archive kept, favourite or non-`OPEN` jobs. Rows archived before migration `r0s1t2u3v4w5` were backfilled: `THRESHOLD` if the score is below the owner's active threshold, otherwise `USER`.
* **Generation Status Rule:** a CV/letter generation remembers the status it started from in `jobs.pre_generation_status`. Completion and failure keep `APPLIED`/`INTERVIEW`/`OFFER`/`ACCEPTED`/`REJECTED` (failure still sets `generation_error`); earlier states become `DRAFTED` / `FAILED`. Cancel restores the stored status. Rule: `core/job_status.py::status_after_generation`.
* **API Deviations (Redesign):** no `/api/v1` prefix, no UUID ids, no unified error envelope. The new client normalises the existing error shapes (spec section 2.4).
* **Server state via TanStack Query (frontend redesign):** the only state library in `frontend/`. WebSocket events update or invalidate query caches in one place (`frontend/src/realtime/applyEvent.ts`); UI state lives in components or the URL. * **Connection tests answer data (phase 7b, G2):** `POST /admin/test/openrouter|ollama` always answer 200 `{ok, reason?, model?, model_found?, available_models?}` with a fixed `reason` code; the raw provider error is only logged, and the web turns each reason into a fixed sentence. The model list answers 502 `openrouter_failed` for any upstream failure and never forwards the upstream status. Why: the web client drops the text of a 5xx, and a forwarded 401 would make it refresh the session and log the admin out.
* **AI error as a code (phase 7b, G3):** `store_ai_404_error(message, code)` stores a code in the Redis key `system:ai_error_code` (`auth`, `rate_limit`, `model_not_found`, `connection`, `server`) next to the legacy text `system:ai_404_error`; `GET /admin/system-status` answers the code (`unknown` when only the old text exists), and the web shows a provider-neutral sentence per code. Why: the web never shows server text, and `_call_openrouter` also stores local-model failures, so an "OpenRouter" text would be wrong as well. `GET /status` keeps the text for the old UI until the cutover (backlog).
* **Admin role test (phase 7b, preflight ruling 10):** `tests/test_company_directory.py::test_every_admin_route_refuses_a_member` is parametrized over the hand list `ADMIN_ROUTES`, and `test_the_admin_route_list_is_complete` collects every route of `app.routes` whose dependency tree contains `get_current_admin_user` and compares it with that list. Why: a new admin route without a member-refusal test fails CI instead of relying on review.

### 5. Open Questions

* **Legacy `jobs.company_domain` values** (job-board hosts, `host:port`) are not normalised; the web shows the domain form. Optional SQL cleanup: see the P2-backend-5 report (not run).
* **Migration `u3v4w5x6y7z8`** (`jobs.generation_started_at`) is only verified against SQLite; jobs already GENERATING when it is applied have no stamp and are not swept.
* **Existing `company_profiles` rows** may contain personalised content from before the privacy change: an admin deletes such a profile per row on its `/companies?domain=` detail ("Profil löschen", phase 7b), or runs the one-off SQL (`DELETE FROM company_profiles;` or `UPDATE company_profiles SET raw_data = NULL, analyzed_at = NULL;`); users then re-run the research.
* **Monolith vs. Microservices:** Should the supervisord structure be split into independent Docker services in the long run?
* **Notification Overrides:** Notification settings are global + per-platform configurable — does this override model remain?
* **Migration not yet run on PostgreSQL:** `r0s1t2u3v4w5`, `s1t2u3v4w5x6` and `t2u3v4w5x6y7` are only verified against SQLite (tests build the schema from the models); the dev container has no PostgreSQL. Run the stack once so startup applies them before relying on them.
* **Deferred backend points (redesign spec section 3):** unified error envelope; `/api/v1` prefix; `crawl_interval_minutes` is stored but unused by the scheduler; Google Drive files cannot be viewed or downloaded in-app; OAuth `state` is the raw user id; notification templates cannot have type `SMTP`.
* **Docker not verified:** `frontend/Dockerfile`, `frontend/Dockerfile.dev` (non-root `node` user, pnpm via `corepack install`) and the `ai-job-agent-frontend` compose services (:3000) were only parsed, `docker compose config` and `docker compose build` have not been run (no Docker in the dev container). Run both on the host before relying on the service.
* **Inbox approximations (G10-G12):** undo of Aussortieren marks the job `kept_by_user`; threshold undo re-applies the previous value; the next-run time uses the browser's time zone, the scheduler the profile's.
* **Hard delete leaves files (R-17, ruling 25):** `DELETE /jobs/{id}` on an archived job removes the job, its history and its document rows, but not legacy on-disk files or Google Drive files. `POST /jobs/bulk-delete` has the same flaw and still also leaves history and document rows (FK error on PostgreSQL); it is unused by the new UI.
* **Legacy `?job=` links (spec 2.3)** of the old UI: the redirect to `/jobs/<id>` was not built; old bookmarks with `?job=` do not open the job.
* **Security - render service SSRF residuals (phase 5, R4/R10):** the render service (Botasaurus, a separate container, `RENDER_API_URL`, outside this repo) is not covered by `core/url_safety.py`. (1) It follows redirects, also to internal hosts. (2) DNS rebinding: the worker checks the canonical name, then the render container resolves it again, so a time-based rebind remains. (3) Page JavaScript and subresource requests in the render browser can reach internal services (full-read SSRF). The fix belongs in the render service (per-request interception that blocks non-public targets, or pinning the resolved address) or in egress isolation of the render container.
* **Security - DNS flood (phase 5):** the guard has 8 resolver threads per process. A flood of never-answering names makes URL checks queue and time out at 3 s each; this fails closed, but legitimate URL checks are refused meanwhile. Rate limiting the URL endpoints would close it.
* **Crawl reaper under load (phase 5):** queue waits mid-pipeline (`filter_urls` on a busy `ai_queue`, detail pages behind another crawl's backlog) count as no progress, so after 15 min a slow crawl ends as a falsely failed run (never a duplicate).
* **Product question - one dead detail link fails the run (phase 5 final wave, I3):** a detail page that cannot be downloaded fails the whole crawl, stores the run as `unreachable` and flags the source as failing (banner, nav badge). The alternative is to count it as skipped (`_mark_scrape_failed`), which gives up detecting a render-service outage. Needs the user's ruling.
* **Scraper API restart alone kills healthy crawls (phase 5, M10):** supervisord restarts the scraper API process on its own after a crash; its startup cleanup then records every live crawl as failed and deletes the hashes, and their workers bail out. Since the final wave the web at least shows the end (`crawl_job_failed`). The real fix needs a worker heartbeat (out of scope).
* **`/scraper/search` with a foreign `platform_id` (phase 5, M9):** the scraper still accepts a client-supplied `platform_id` without an owner check. It is neutralised downstream: `filter_urls` reads only the crawl user's platform (a foreign id yields no URLs) and `_save_last_run` is owner-checked. An owner check at `/search` itself would close it at the boundary.
* **Queued crawl that dies by TTL ends silently (phase 5 final wave):** a crawl still queued (`starting`) whose hash expires after `CRAWL_TTL_SECONDS` leaves no run record and publishes no event, so the web keeps it running until a reload. The reaper's limit for queued crawls equals the hash TTL (`CRAWL_TTL_SECONDS`), so the reaper effectively never ends a queued crawl before Redis expires it; a shorter queued limit (or a TTL longer than it) would let the reaper record and announce it.
* **Single-node Redis (phase 5):** the crawl Lua scripts (`RELEASE_SCRIPT`, `PROGRESS_SCRIPT`) assume single-node Redis; they are not Redis-Cluster-safe without hash tags.
* **Recreate the dev DB (phase 5):** a database that ran `alembic upgrade head` on the Task 3 version of migration `v4w5x6y7z8a9` (before the `ON DELETE CASCADE` edit) must be recreated, or the `platform_runs.platform_id` FK altered by hand. Migration `v4w5x6y7z8a9` is verified on SQLite only (downgrade not executed).
* **Phase 5 drops to confirm (G17):** the job-count link, the favicon and "cancel all crawls" are dropped. Reported to the user as reversible.
* **Security - request body size before the upload check (phase 6, S-3):** Starlette parses the whole multipart body into a `SpooledTemporaryFile` (disk above 1 MB) before `read_upload` runs, so memory is bounded but request size and temp-disk use are not. No proxy body limit exists in the repo; set one (e.g. `client_max_body_size`) in front of the API.
* **AI prompt size (phase 6, T2 M8/M9):** every profile field is bounded, but the aggregate prompt (all fields plus a 30,000-character CV) has no bound, and Ollama's `num_ctx` (not set anywhere) may be smaller than a full CV plus the prompt, so local routing can truncate the input silently.
* **Security - template upload cost (phase 6 final review, M10):** `POST /document-templates` has no rate limit, and every CV template upload sends up to 1,000,000 characters of HTML to the AI annotator, whose call sets no `max_tokens` (`annotate_cv_template_with_jinja2`). Pre-existing and authenticated; decide on a rate limit and a token cap.
* **CV import timeout on reasoning models (phase 6 final review, M9):** the import uses the shared client (OpenRouter 120 s x 2 attempts). With `CV_PARSE_MAX_TOKENS` 16,000 a reasoning model can need more than 120 s, so a long CV answers 502 after about 4 minutes, and the global "Verbindung zu OpenRouter fehlgeschlagen" banner is raised because `APITimeoutError` is an `APIConnectionError`. Not measured; needs a per-call timeout decision (e.g. `client.with_options(timeout=..., max_retries=0)`).
* **Soft time limit becomes an AI-banner error (phase 6 final review, M11):** the OpenAI SDK wraps `SoftTimeLimitExceeded` into `APIConnectionError` after its retry, so a generation that hits its soft limit records `OPENROUTER_ERROR` or the failed text instead of `GENERATION_TIMEOUT_ERROR`, and `_call_openrouter` sets the global connection banner. All texts are fixed; the fix belongs to the shared AI wrapper.
* **CV import duration with local routing (phase 6, R-8):** the import is a sync endpoint; with `job_analysis` routed to Ollama it can hold a threadpool worker for up to 600 s (`OLLAMA_REQUEST_TIMEOUT_SECONDS`), and the browser waits as long.
* **Queued template fill counted as stalled (phase 6):** the web's 15-minute stall clock starts at the template's `updated_at` (set at upload; the fill writes it only at its end), so queue wait counts. A fill that waits more than about 90 s behind a busy `ai_queue` before its 810 s run can show "stalled" (delete and re-upload offered) while it still finishes later.
* **Unparseable `cv_data` entry is dropped by the next save (phase 6, R15):** the web reads a stored entry in an odd shape as empty (lenient parse, so a legacy row never breaks the page), and the next Lebenslauf save, which sends the whole `cv_data`, removes it. By design (B2); revisit if legacy rows turn up.
