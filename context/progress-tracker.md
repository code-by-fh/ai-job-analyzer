### 4. Key Architectural Decisions (ADRs)

* **OpenRouter Config:** Stored in DB (`system_settings`), not in `.env` (dynamic model switches via UI).
* **Process Isolation:** Separate queue model (`ai_queue` vs. `scraper_queue`); Playwright crawls do not block AI tasks.
* **Single-Container Deployment:** All 4 backend processes via `supervisord` in a single Docker container.
* **Deferred Platform Creation:** Platform is only created upon completion of the setup wizard (no `pending_setup` overhead).
* **URL-Pattern Inference:** Character-wise common prefix (`os.path.commonprefix`) with trim to the last natural separator — more robust than a segment-wise approach for boards with IDs in the path.
* **Status Transition Table:** `server/core/job_status.py::ALLOWED_TRANSITIONS` is the single source for user status changes. It is permissive (backward moves and skips are allowed and always recorded in `job_status_history`). `SEEN`, `GENERATING` and `FAILED` can never be a target (400); `SEEN` and `GENERATING` cannot be left by hand (409); unknown legacy values may move to any user status. A status change on an archived job restores it. The web `domain/` mirror must match this table.
* **Archive Reason:** `jobs.archive_reason` (`THRESHOLD` | `USER`) separates "Unter Schwellwert" from "Von dir aussortiert". Any user restore sets `jobs.kept_by_user`, and threshold runs never archive kept, favourite or non-`OPEN` jobs. Rows archived before migration `r0s1t2u3v4w5` were backfilled: `THRESHOLD` if the score is below the owner's active threshold, otherwise `USER`.
* **Generation Status Rule:** a CV/letter generation remembers the status it started from in `jobs.pre_generation_status`. Completion and failure keep `APPLIED`/`INTERVIEW`/`OFFER`/`ACCEPTED`/`REJECTED` (failure still sets `generation_error`); earlier states become `DRAFTED` / `FAILED`. Cancel restores the stored status. Rule: `core/job_status.py::status_after_generation`.
* **API Deviations (Redesign):** no `/api/v1` prefix, no UUID ids, no unified error envelope. The new client normalises the existing error shapes (spec section 2.4).
* **Server state via TanStack Query (frontend redesign):** the only state library in `frontend/`. WebSocket events update or invalidate query caches in one place (`frontend/src/realtime/applyEvent.ts`); UI state lives in components or the URL. Why: hand-written caches were the main source of stale state in the old UI.
* **Frontend redesign - recorded deviations:** (1) no `/api/v1` prefix, UUID ids or unified error envelope; the client normalises the existing shapes (`{detail: string}`, `{detail: [...]}`, 429 `{error}`, scraper `200 + {status: "error"}`) into one `ApiError`. Why: large cross-cutting backend change not needed for the redesign. (2) No committed `.npmrc` with a private registry; Docker builds use the public registry, the dev container sets it via the environment. Why: private project, builds must work for anyone. (3) Node 22 instead of Node 20 (end-of-life; Vitest 5 and jsdom 30 need 22). (4) Prototype component CSS is ported as global `@layer components` classes; Tailwind utilities (mapped to the tokens via `@theme inline`) are used for layout. Why: 1:1 fidelity with the prototype and token re-mapping inside the ink sidebar and toasts. (5) Login field is "Benutzername", not the prototype's "E-Mail", because the API authenticates usernames.
* **Frontend redesign - accessibility over 1:1 prototype fidelity:** spec 4.3 #5 binds where the prototype deviates. Interactive control borders use `--line-control` (>= 3:1), not `--line-strong` (about 1.8:1); static `.tag` keeps the hairline. Errors on the ink sidebar use `--sb-danger`. Seg and Tabs focus rings are inset so `overflow` does not clip them. Mobile text and hit targets follow the 13 px / 44 px rules.
* **Frontend redesign - error text policy:** `describeError` returns a generic translated message per error code and never the server `detail`; a caller may opt in with an explicit per-call mapping (allow-list). Why: spec 6 "never show raw server internals". `safeNextPath` rejects control characters and off-origin targets (checked by URL parsing against the origin).
* **Frontend redesign - layers and live regions:** `frontend/src/ui/layerStack.ts` is the one dismiss stack shared by `ModalLayer` and `Popover` (only the top layer handles Escape and Tab); scroll lock is ref-counted; toasts use persistent live regions (`status` for info/success, `alert` for errors). A busy `Button` blocks activation but stays focusable (`aria-disabled`).
* **Frontend redesign - realtime:** `job_analysis_finished` is a progress update (analysis step, count never moves backwards); the activity task ends only on `crawl_job_completed` / `crawl_job_failed` / `crawl_job_cancelled`, and late events for ended crawls are ignored (`endedIds`). A reconnect re-seeds running tasks from `GET /scraper/crawl-status` and keeps the last finished task. `job_updated` / `job_update` also invalidate the nav counts. `template_ready` carries `{type, template_id, user_id}` (`server/workers/tasks/fill_cv_template.py`).
* **Frontend redesign - logout:** after `POST /auth/logout` settles (success or failure) the app does a full navigation to `/login` (`window.location.assign`), never `queryClient.clear()` plus `router.replace`. Why: clearing while the shell is mounted refetched `/me` with dead cookies and ended on `/login?next=...`; the full navigation also closes the socket.
* **Frontend redesign - API client bodies:** `ApiRequest` takes `json`, `form` (urlencoded) or `formData` (multipart, no explicit Content-Type so the browser sets the boundary). `requestBlob` sends `Accept: */*` and returns `{blob, filename}` (filename from `Content-Disposition`, `filename*` first) with the same refresh/retry and error normalisation. Cross-origin, the filename is only readable if the API lists `Content-Disposition` in `Access-Control-Expose-Headers`.
* **Frontend redesign - e2e rules:** the Playwright `auto` fixtures fail a test on any unmocked API call and on any `console.error` / uncaught page error; a test that provokes the browser's 401 log line on purpose opts in with `allowedConsoleErrors: [EXPECTED_SESSION_PROBE]`; response fixtures are typed with `z.input` of the real zod schemas; a first-paint test checks the stored theme before the first frame.
* **Frontend redesign - job page rulings (phase 2):** (D1) PDFs are fetched through the API client (`/jobs/{id}/documents/{doc}/view`) and shown from `blob:` URLs in `<object>`, because the API keeps `X-Frame-Options: DENY`; the blob type is pinned to the document's mime type or `application/pdf`, the URL is created and revoked in an external store (`useDocumentFile`), browsers without an inline PDF viewer get "PDF öffnen"/download. (D2) "Phase ändern" is a WAI-ARIA menu button (`ui/Menu.tsx`), not a dialog (since Feedback 1 T13 a full-size trigger on the track's row; the menu stays because the guards differ per target). (D4/G9) "Selbst abgesagt" is `REJECTED` plus a history note; a back-dated apply date goes into the status note (G10). (D5/G2) `interview_at` is the interview date (phase INTERVIEW and `nextStep` input); `next_follow_up_at` stays "Nachfassen am" ("Antwort bis" in OFFER); "Datum entfernen" sends an explicit `null`. (D6/G1) No fit-feedback form (no backend). (D8) CV notes travel in `jobs.cv_draft`. (G5/G6) No intermediate generation steps; interview prep and research turn "stalled" after 3 minutes with a retry because the backend publishes no failure event. Background tasks without server state live in the `["pending-tasks"]` query entry that `applyEvent` finishes.
* **Job page phase flow (Feedback 1 - T13):** (R1) the tab after a phase change is one rule, `tabAfterStatusChange(status)` in `features/job/tabs/jobTabs.ts`, applied by `useChangeStatus` after every successful change (menu, dialog, next-step card, apply checklist; not the toast's undo); statuses without an entry keep the tab. (R2) "Einladung eintragen" still sets Interview directly (no phase dialog) and then opens the "Termine & Daten" drawer on the interview date, so the date is asked once, in the place that also edits it later. (R3) The phase dialog's interview fields start empty; an empty or unreadable day sends nothing (never `null`), a stored date is named in the hint; the PATCH runs after the status change, and its failure only toasts a fixed sentence (the status stays). (R4) The interview fields appear in every dialog whose target is Interview (also skip, backward and without documents); a plain one-step move to Interview gets its own `askInterviewDate` guard.
* **Offer outcome tabs (Feedback 1 - T14):** (R1) REJECTED is reached by an employer's rejection, "Selbst abgesagt" and "Angebot abgelehnt" (D4), so "Wie geht's weiter" is neutral and its quotes fit all three. (R2) Quotes come from a local curated DE/EN list (`outcome/quotes.ts`, no API: CSP, privacy, offline); the first one is stable per job id, "Anderer Spruch" cycles. (R3) One `outcome_notes` column serves both tabs (a job holds one outcome); the first-day checklist is its own JSON column with fixed keys, the start date a SQL `DATE` (a calendar day, no instant). (R4) The celebration is CSS-only (no dependency), plays after any successful change to ACCEPTED from this page (not on realtime updates or undo), is `aria-hidden` and hidden under reduced motion, where the tab's "Glückwunsch" heading is the static success message. (R5) A closed job opens on its outcome tab; an outcome tab in the address that does not fit the status falls back to the default. (R6) Extras: the start date names the countdown ("in 25 Tagen"), the first-day checklist links to the applications until the others are withdrawn, and "Zum Eingang" names the inbox's new matches.
* **Notification service (Feedback 1 - T15):** (R1) SQLite on a volume with `create_all` at startup: the smallest durable store for one table; the first schema change brings Alembic (or Postgres). (R2) All field values of a channel, not only the secrets, are one Fernet token, so a leaked database file shows no recipients or hosts either. (R3) `.env` holds one `NOTIFY_API_KEY`; compose builds `NOTIFY_API_KEYS=ai-job-agent:<key>` from it, so the server key and the service key cannot drift. (R4) Two networks (security review fix): `notify` is `internal: true` and joined only by the server and the service; egress to the providers goes through `notify_egress`, which only the service joins. No host port. (R5) Test sends and notifications answer 200 with `delivered` plus a fixed `reason` per channel (like the admin AI tests), not a 5xx. (R6) SMTP now verifies the certificate on STARTTLS (the old adapter called `starttls()` without a context, which does not verify), and implicit TLS (465) is not supported, as before. (R7) Internationalised SMTP host names must be entered as punycode (no `idna` dependency). (R8) The job digest sends one push per job on Pushover (the old per-match push) and one HTML mail on e-mail channels; request `recipients` replace a channel's default list (the per-source recipient lists of today).
* **Notification service wiring (Feedback 1 - T16):** (R1) The service owner of a user is `u_` + 32 hex digits of SHA-256(`ai-job-agent/notification-owner/<user id>`): stable (no secret to rotate), derived only from the authenticated user, and not the raw id; it is not a secret, isolation comes from the API key plus the server deriving it. The API exposes only `<x>_running` and `<x>_error`; the client prefers the server state over its pending task (`prepPhase`). Why not reuse `status=GENERATING`: the prep runs beside the application status and must not block status changes. Queue time counts (unlike generations); a late worker overwrites a swept error with its result. Company research (T2) reuses it on the job (`jobs.company_research_started_at` / `company_research_error`, `core/company_research_state.py`, `jobResearchPhase`); it lives on the job, not on the shared profile, because a research may start before any domain (and profile row) exists and its error belongs to the user who started it. The error column holds fixed codes (`DOMAIN_NOT_FOUND`, `RESEARCH_FAILED`) the web maps to its own texts.
* **Template live state (phase 6, D10):** `template_ready` invalidates the `["templates"]` prefix (list and previews), a socket reconnect refetches active queries, and a processing card turns "stalled" after 15 minutes (`TEMPLATE_STALL_MS`); no polling and no status in the event. Why: the server writes the state before it publishes, so a refetch is always right, and the stall rule covers a hard-killed worker, the one end without an event.
* **Frontend redesign - provisional product decisions (phase 6, R1 and C-10, reversible):** reported to the user, who can veto: no re-score button (needs a bulk re-analysis endpoint); the CV import keeps replacing role, skills, location and minimum salary when the CV names them, with a confirm when CV content exists; dropped for lack of backend fields: the Arbeitsmodell seg and location chips, the per-document "Bei Bewerbungen beilegen", and DOCX/PDF template upload (HTML only); dropped from the old UI: the full-screen template preview, the "Zuletzt geändert am" deck line (G12) and the 8-field completion percentage (replaced by the gaps hint).
* **Job sub-resources under one key:** everything of a job is cached under `["job", id, ...]` (detail, history, documents, stored HTML), so one realtime invalidation refreshes all of it; PDF bytes live under `["job-file", jobId, docId, uploaded_at]` and never refetch for the same version.
* **Notification templates in sources stay copies (phase 7a, R1, provisional):** a source stores the template text it was given (`pushover_template`, `resend_template`, ...), not a reference. Editing or deleting a template in Einstellungen changes no source; the editor says so, the drawer offers the kept text as "Eigene Vorlage (beibehalten)" and the user re-picks to adopt a change. Why: this keeps the existing data model (no migration, no dangling reference on delete). Reversible; the user is asked (Open Questions).
* **Reset scope and delete order (phase 7a, R1/R8, provisional):** "Profil zurücksetzen" (`DELETE /settings`) empties only Ziel and Lebenslauf (no demo values, so the onboarding asks again) and keeps channels, templates and proofs. "Alles zurücksetzen" (`DELETE /user/reset`) deletes everything the account owns except the account: jobs, sources, run history, the profile row (credentials, language, time zone), proofs, own CV and notification templates; global templates stay. All account deletes go through `services/user_data.py`, children before parents (history and documents, then jobs; foreign jobs detached from own sources, runs, then sources; proofs and templates; the profile; `delete_user` also nulls `changed_by` in other accounts' history), so PostgreSQL's foreign keys never refuse it (R-17); the tests run SQLite with `PRAGMA foreign_keys=ON` to see the same errors. The reset lands on `/inbox` by a full navigation, which shows the onboarding and drops the old cache. Reversible; the user is asked (Open Questions).
* **Company directory per user (phase 7b, G6/R1, provisional):** `GET /companies` lists only the domains of the caller's own non-`SEEN` jobs, with or without a profile (`services/company_directory.py`, never loading `raw_data`); `?scope=all` is admin-only (403 for members) and adds every stored profile. The profiles themselves stay shared per domain (`GET /companies/{domain}`, phase 2), and the global search is own-data only, also for admins. Why: the old endpoint sent every profile of the installation with its full JSON to every user, which showed what other users research. Reversible; the user is asked (7b-Q1).
* **Connection tests answer data (phase 7b, G2):** `POST /admin/test/openrouter|ollama` always answer 200 `{ok, reason?, model?, model_found?, available_models?}` with a fixed `reason` code; the raw provider error is only logged, and the web turns each reason into a fixed sentence. The model list answers 502 `openrouter_failed` for any upstream failure and never forwards the upstream status. Why: the web client drops the text of a 5xx, and a forwarded 401 would make it refresh the session and log the admin out.
* **AI error as a code (phase 7b, G3):** `store_ai_404_error(message, code)` stores a code in the Redis key `system:ai_error_code` (`auth`, `rate_limit`, `model_not_found`, `connection`, `server`) next to the legacy text `system:ai_404_error`; `GET /admin/system-status` answers the code (`unknown` when only the old text exists), and the web shows a provider-neutral sentence per code. Why: the web never shows server text, and `_call_openrouter` also stores local-model failures, so an "OpenRouter" text would be wrong as well. `GET /status` keeps the text for the old UI until the cutover (backlog).
* **Admin role test (phase 7b, preflight ruling 10):** `tests/test_company_directory.py::test_every_admin_route_refuses_a_member` is parametrized over the hand list `ADMIN_ROUTES`, and `test_the_admin_route_list_is_complete` collects every route of `app.routes` whose dependency tree contains `get_current_admin_user` and compares it with that list. Why: a new admin route without a member-refusal test fails CI instead of relying on review.
* **Swappable page renderer (render service swap, R1):** the crawl renders pages through `services/page_rendering/`: a `PageRenderer` protocol (`fetch_html(url) -> str | None`, never raises), one adapter per render service, and `get_page_renderer()` choosing it by `RENDER_SERVICE` from a name registry. Callers import only the package, so another render service is one new adapter plus an env value, with no caller changes.
* **Render timeouts 45 s / 90 s (render service swap, R3):** the adapter asks for a 45 s render budget; page-render-service queues a request for up to 20 s for a per-host slot and 20 s for a free browser outside that budget, so the HTTP timeout (`RENDER_API_HTTP_TIMEOUT`, 90 s) stays above 45 + 40 s and a queued render is not cut off by the client. The preview timeout in `routers/platforms.py` builds on `HTTP_TIMEOUT_SECONDS`.

### 5. Open Questions

* **Legacy `jobs.company_domain` values:** migration `x6y7z8a9b0c1` clears every value equal to the job's posting host that has no researched profile; other legacy values (`host:port`) stay and the web shows the domain form. The migration's data step is only verified against SQLite.
* **Migration `u3v4w5x6y7z8`** (`jobs.generation_started_at`) is only verified against SQLite; jobs already GENERATING when it is applied have no stamp and are not swept.
* **Existing `company_profiles` rows** may contain personalised content from before the privacy change: an admin deletes such a profile per row on its `/companies?domain=` detail ("Profil löschen", phase 7b), or runs the one-off SQL (`DELETE FROM company_profiles;` or `UPDATE company_profiles SET raw_data = NULL, analyzed_at = NULL;`); users then re-run the research.
* **Monolith vs. Microservices:** Should the supervisord structure be split into independent Docker services in the long run?
* **Migration not yet run on PostgreSQL:** `r0s1t2u3v4w5`, `s1t2u3v4w5x6` and `t2u3v4w5x6y7` are only verified against SQLite (round 2's `c1d2e3f4a5b6`, `d2e3f4a5b6c7` and `e3f4a5b6c7d8` are in the Next Up check) (tests build the schema from the models); the dev container has no PostgreSQL. Run the stack once so startup applies them before relying on them.
* **Deferred backend points (redesign spec section 3):** unified error envelope; `/api/v1` prefix; `crawl_interval_minutes` is stored but unused by the scheduler; notification templates cannot have type `SMTP`.
* **Docker not verified:** `frontend/Dockerfile`, `frontend/Dockerfile.dev` (non-root `node` user, pnpm via `corepack install`) and the `ai-job-agent-frontend` compose services (:3000) were only parsed, `docker compose config` and `docker compose build` have not been run (no Docker in the dev container). Run both on the host before relying on the service.
* **Inbox approximations (G10-G12):** undo of Aussortieren marks the job `kept_by_user`; threshold undo re-applies the previous value; the next-run time uses the browser's time zone, the scheduler the profile's.
* **Hard delete leaves files (R-17, ruling 25):** `DELETE /jobs/{id}` on an archived job removes the job, its history and its document rows, but not legacy on-disk files. `POST /jobs/bulk-delete` has the same flaw and still also leaves history and document rows (FK error on PostgreSQL); it is unused by the new UI.
* **Legacy `?job=` links (spec 2.3)** of the old UI: the redirect to `/jobs/<id>` was not built; old bookmarks with `?job=` do not open the job.
* **Security - render service SSRF residuals (phase 5, R4/R10; updated with the render service swap):** the render service (page-render-service, a separate container, `RENDER_API_URL`, outside this repo) is not covered by `core/url_safety.py`, which only checks the URL before it is sent. The old residuals (1) redirects to internal hosts, (2) DNS rebinding between the worker's check and the render container's own resolution, (3) page JavaScript and sub-resource requests reaching internal services are now handled by the service itself: its egress proxy blocks private and reserved targets for redirects, sub-resources and rebinding, unless `ALLOW_PRIVATE_TARGETS=true` (compose leaves it at the default false). Still open: verify that guard against the real image in a running stack (a redirect to an internal host and an internal sub-resource must both be blocked).
* **Render service busy or flaky fails the crawl (render service swap, R4):** the adapter does not retry, so 429 `SERVICE_BUSY` (queue full, `Retry-After`) or a transient 502 (`NAVIGATION_FAILED`, `TARGET_BLOCKED`) returns None and, for a detail page, fails the whole crawl (see the dead-detail-link question below). A retry honouring `Retry-After` within the worker's time budget is the candidate fix; needs a ruling.
* **Docker stack with page-render-service not verified (render service swap):** the `ai-job-agent-page-render` service (image `doublelayer/page-render-service:latest`, read-only rootfs and tmpfs mounts, `API_KEYS` from `RENDER_API_KEY`) and the server's `RENDER_*` env were only parsed as YAML; `docker compose config`, a container start and a real crawl through the service have not been run (no Docker in the dev container).
* **Security - DNS flood (phase 5):** the guard has 8 resolver threads per process. A flood of never-answering names makes URL checks queue and time out at 3 s each; this fails closed, but legitimate URL checks are refused meanwhile. Rate limiting the URL endpoints would close it.
* **Crawl reaper under load (phase 5):** queue waits mid-pipeline (`filter_urls` on a busy `ai_queue`, detail pages behind another crawl's backlog) count as no progress, so after 15 min a slow crawl ends as a falsely failed run (never a duplicate).
* **Product question - one dead detail link fails the run (phase 5 final wave, I3):** a detail page that cannot be downloaded fails the whole crawl, stores the run as `unreachable` and flags the source as failing (banner, nav badge). The alternative is to count it as skipped (`_mark_scrape_failed`), which gives up detecting a render-service outage. Needs the user's ruling.
* **Scraper API restart alone kills healthy crawls (phase 5, M10):** supervisord restarts the scraper API process on its own after a crash; its startup cleanup then records every live crawl as failed and deletes the hashes, and their workers bail out. Since the final wave the web at least shows the end (`crawl_job_failed`). The real fix needs a worker heartbeat (out of scope).
* **`/scraper/search` with a foreign `platform_id` (phase 5, M9):** the scraper still accepts a client-supplied `platform_id` without an owner check. It is neutralised downstream: `filter_urls` reads only the crawl user's platform (a foreign id yields no URLs) and `_save_last_run` is owner-checked. An owner check at `/search` itself would close it at the boundary.
* **Queued crawl that dies by TTL ends silently (phase 5 final wave):** a crawl still queued (`starting`) whose hash expires after `CRAWL_TTL_SECONDS` leaves no run record and publishes no event, so the web keeps it running until a reload. The reaper's limit for queued crawls equals the hash TTL (`CRAWL_TTL_SECONDS`), so the reaper effectively never ends a queued crawl before Redis expires it; a shorter queued limit (or a TTL longer than it) would let the reaper record and announce it.
* **Single-node Redis (phase 5):** the crawl Lua scripts (`RELEASE_SCRIPT`, `PROGRESS_SCRIPT`) assume single-node Redis; they are not Redis-Cluster-safe without hash tags.
* **Recreate the dev DB (phase 5):** a database that ran `alembic upgrade head` on the Task 3 version of migration `v4w5x6y7z8a9` (before the `ON DELETE CASCADE` edit) must be recreated, or the `platform_runs.platform_id` FK altered by hand. Migration `v4w5x6y7z8a9` is verified on SQLite only (downgrade not executed).
* **Phase 5 drops to confirm (G17):** the job-count link, the favicon and "cancel all crawls" are dropped. Reported to the user as reversible.
* **Security - request body size before the upload check (phase 6, S-3):** Starlette parses the whole multipart body into a `SpooledTemporaryFile` (disk above 1 MB) before `read_upload` runs, so memory is bounded but request size and temp-disk use are not. No proxy body limit exists in the repo; set one (e.g. `client_max_body_size`) in front of the API.
* **AI prompt size (phase 6, T2 M8/M9):** every profile field is bounded, but the aggregate prompt (all fields plus a 30,000-character CV) has no bound, and Ollama's `num_ctx` (not set anywhere) may be smaller than a full CV plus the prompt, so local routing can truncate the input silently.
* **Security - template upload cost (phase 6 final review, M10):** `POST /document-templates` has no rate limit, and every CV template upload sends up to 1,000,000 characters of HTML to the AI annotator, whose call sets no `max_tokens` (`annotate_cv_template_with_jinja2`). Pre-existing and authenticated; decide on a rate limit and a token cap.
* **CV import timeout on reasoning models (phase 6 final review, M9):** the import uses the shared client (OpenRouter 120 s x 2 attempts). With `CV_PARSE_MAX_TOKENS` 16,000 a reasoning model can need more than 120 s, so a long CV answers 502 after about 4 minutes, and the global "Verbindung zu OpenRouter fehlgeschlagen" banner is raised because `APITimeoutError` is an `APIConnectionError`. Not measured; needs a per-call timeout decision (e.g. `client.with_options(timeout=..., max_retries=0)`).
* **Soft time limit becomes an AI-banner error (phase 6 final review, M11):** the OpenAI SDK wraps `SoftTimeLimitExceeded` into `APIConnectionError` after its retry, so a generation that hits its soft limit records `OPENROUTER_ERROR` or the failed text instead of `GENERATION_TIMEOUT_ERROR`, and `_call_openrouter` sets the global connection banner. All texts are fixed; the fix belongs to the shared AI wrapper.
* **CV import duration with local routing (phase 6, R-8):** the import is a sync endpoint; with `job_analysis` routed to Ollama it can hold a threadpool worker for up to 600 s (`OLLAMA_REQUEST_TIMEOUT_SECONDS`), and the browser waits as long.
* **Queued template fill counted as stalled (phase 6):** the web's 15-minute stall clock starts at the template's `updated_at` (set at upload; the fill writes it only at its end), so queue wait counts. A fill that waits more than about 90 s behind a busy `ai_queue` before its 810 s run can show "stalled" (delete and re-upload offered) while it still finishes later.
* **Unparseable `cv_data` entry is dropped by the next save (phase 6, R15):** the web reads a stored entry in an odd shape as empty (lenient parse, so a legacy row never breaks the page), and the next Lebenslauf save, which sends the whole `cv_data`, removes it. By design (B2); revisit if legacy rows turn up.
* **Phase 6 product decisions to confirm (R1, C-10):** see the ADR "provisional product decisions (phase 6)"; all reversible.
* **Phase 7a product questions to confirm (R1, preflight ruling 50; all reversible):** (Q1) template copies in sources stay copies, and the editor says to re-pick (ADR "Notification templates in sources stay copies"); (Q2) "Alles zurücksetzen" deletes everything the account owns except the account, proofs and own templates included (ADR "Reset scope and delete order"); (Q3) the old UI's SMTP provider presets, the Pushover link and the Resend setup guide are dropped; (Q4) the factory-reset text appears twice, in the Gefahrenzone and again in its confirmation dialog (could be shortened in the zone).
* **Phase 7b product questions to confirm (R1, R7, preflight rulings 32a/33; all reversible):** (7b-Q1) the company directory and the search list only the companies of the user's own jobs, and admins switch to every company with "Alle Firmen dieser Installation" (ADR "Company directory per user"); (7b-Q2) user management stays as today: no admin creation, no role changes and no password resets by an admin (G11); (7b-Q3, provisional) the stored AI error shows only in Einstellungen › Systemfehler, with no app-wide banner as in the old UI (a later shell `Notice` for admins could read the same `systemStatusQueryOptions`).
* **Phase 4 open points:** (G7) no score column and (G12) no platform filter, sort control or bulk archive per company in `/applications` (veto possible, see the ADR); (G14) the search covers title and company only, not description or notes. Final wave (resolved): fixed - the closed busy bar is suppressed under the toggle (one bar per page), the reduced-motion capture is taken at 1440, the search clear glyph is in the palette (grey mask on `.input[type="search"]`), `MASTHEAD_TITLE_SELECTOR` lives in `ui/Masthead` (the strip no longer imports an inbox module), five exports with no outside user are file-local, the FakeServer rejects unknown patch fields and defaults to date sort, navDue asserts card = badge. Dropped - container query for the strip (the constraint says `@media`; measured and e2e-guarded), ghost strip height at 768-959 px (needs 22+ applications in one phase), FakeServer 422/history order/restore/409 (capped at the source, the UI sorts itself, no restore journey, `refused` is asserted), ACME row selection and journey gaps (covered by phase 2 specs).

* **Notification service not run in Docker (Feedback 1 - T15):** `notification-service/Dockerfile` and the `ai-job-agent-notify` compose service (read-only rootfs, `notify` network, `notify_data` volume, healthcheck) were only parsed as YAML; the tests ran on Python 3.13 (the image is 3.11).
