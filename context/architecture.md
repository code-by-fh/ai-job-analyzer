# AI Job Agent - System Architecture

Factual and concise system architecture documentation for developers and AI agents.

## 1. Process Model & Stack
* **Container Orchestration:** A single container manages services via `supervisord` with the following active processes:
  1. `uvicorn` (Port 8080): Main FastAPI backend (`main.py`) serving REST endpoints, WebSockets (`/ws`), and JWT authentication. Its `RequestValidationError` handler keeps FastAPI's 422 shape `{"detail":[...]}` but drops each error's `input` and `ctx.error`, so a rejected body (e.g. a 1 MB template) is never echoed back.
  2. `scraper_api`: Internal FastAPI service (`scraper_api.py`, internal Port 8081) for validation and crawl control.
  3. `celery` (`ai_queue`): Processes AI assessment, document packaging, notifications, and runs the Celery Beat (`-B`) scheduler.
  4. `scraper_celery` (`scraper_queue`): Executes BeautifulSoup4 crawls of pages rendered by the external page render service (`services/page_rendering/`).
* **Services Stack:**
  - **Database:** PostgreSQL 15 (SQLAlchemy 2.0 ORM, Alembic migrations).
  - **Message Broker & Task Queue:** RabbitMQ (Celery Broker; `CELERY_BROKER_URL` is `amqp://...` in both compose files. Both Celery apps read it from `core/celery_broker.py`, whose default when the variable is unset is the compose RabbitMQ `amqp://guest:guest@ai-job-agent-rabbitmq:5672//`, so the scraper app and the ai worker never split across brokers).
  - **Cache & Pub/Sub:** Redis (Celery result backend, WS messaging, crawl progress state, crawl deduplication, the crawl registry `user:{id}:active_crawls` and the per-source crawl lock `crawl_lock:{user}:{platform}`, and the stored AI error: the legacy text `system:ai_404_error` plus its code `system:ai_error_code`, phase 7b). Redis is not the Celery broker. The crawl Lua scripts assume single-node Redis.
  - **LLMs:** Cloud models via OpenRouter (job analysis, cover letter, research) and local models via Ollama (tailored CV generation). Client limits (`intelligence/service.py`): OpenRouter `AI_REQUEST_TIMEOUT_SECONDS` 120 s with `AI_MAX_RETRIES` 1, Ollama `OLLAMA_REQUEST_TIMEOUT_SECONDS` 600 s with `OLLAMA_MAX_RETRIES` 0. In both cases the worst case stays below the 900 s crawl stall threshold, which a test pins.
  - **Frontend:** `frontend/` (Next.js 16 App Router, React 19, Tailwind CSS v4, TanStack Query; no component libraries), compose service `ai-job-agent-frontend` on port 3000 (`ALLOWED_ORIGINS` default `http://localhost:3000`), built as a standalone server (`frontend/Dockerfile`, Node 22) whose API URL is injected at start by `frontend/env.sh`.

## 2. Directory Layout & Key Boundaries
* `notification-service/` (Feedback 1 - T15) — standalone FastAPI service (own Dockerfile, requirements, tests; imports nothing from `server/`), compose service `ai-job-agent-notify` on port 8000, no host port, reachable only over the `internal: true` network `notify` that only the server and the service join; the service alone also joins `notify_egress` for the providers. An internal network supplies no gateway, so each takes its default route from its non-internal network; egress checks in README "Troubleshooting" (Feedback 2 - T1). Non-HTTP scopes (WebSocket) are refused. It holds the channels and all sending logic: Pushover, Resend, Mailjet, SMTP adapters (`app/delivery/`) and the digest rendering ported from `server/workers/notifications/templates.py` (`app/templates.py`, same hardening). API under `/v1` (`GET /v1/channel-types`, CRUD `/v1/channels`, `POST /v1/channels/{id}/test`, `POST /v1/notifications`, `POST /v1/previews` (T16: renders a digest, sends nothing), contract in `notification-service/README.md`); every route except `GET /health` needs `Authorization: Bearer <key>` from `NOTIFY_API_KEYS` (`app_id:key` pairs, checked in an ASGI middleware before routing and before the body is read, constant-time). Channels are scoped by the key's `app_id` plus an opaque `owner` the app passes; another app's or owner's channel is a 404. All field values of a channel are one Fernet token (`NOTIFY_ENCRYPTION_KEY`; MultiFernet with the optional `NOTIFY_ENCRYPTION_KEY_OLD` for rotation, every channel re-encrypted at startup while it is set) in a SQLite file (mode 0600) on the `notify_data` volume (schema by `create_all` on startup in v1); secrets are write-only (`"set"` / `"not set"`). SMTP hosts must resolve to public addresses on save and again at send time, and the SMTP socket is pinned to the checked address with STARTTLS and certificate verification (`app/net_safety.py`, adapted from `core/url_safety.py`). Limits: test sends 5/min per app and owner plus 20/min per app, notifications 120/min per app; SMTP credentials are printable ASCII (`ascii_text`) (in memory, one process). Until Task 16 the server still sends through `workers/notifications/`; it will read `NOTIFY_API_URL` / `NOTIFY_API_KEY` (already in both compose files).
* `server/core/` — Cross-cutting concerns: `auth.py` (JWT & Token Versioning), `connection_manager.py` (WebSockets), `celery_config.py`, `logger.py` and `job_status.py` (status transition table, archive/restore rules, the generation status rule and the `STATUS_SEEN` constant, shared by routers and workers), `url_safety.py` (SSRF guard, see section 4), `crawl_registry.py` (crawl registry, lock and heartbeat, see `workers/`; also `SCRAPER_START_TIMEOUT_SECONDS`, DNS bound + 2 s, the one wait for a scraper crawl start used by the API and the scheduler), `celery_broker.py` (the one `BROKER_URL` of both Celery apps), `uploads.py` (user uploads: `read_upload` / `read_upload_sync` read at most `max_bytes` + 1 bytes (default `MAX_UPLOAD_BYTES`, 10 MiB) and refuse more with 413 `file_too_large`; `require_type` checks the magic bytes against the declared or expected type (PDF, PNG, JPEG, WebP, DOC, DOCX) and refuses with 415 `unsupported_type`; the client's file name and declared type are never echoed; `content_disposition` builds every file download header of profile and job documents, an ASCII fallback plus RFC 5987 `filename*`, so a quote cannot break the header and a non-Latin-1 name cannot make Starlette raise; `field_error` shapes a fixed 422 item like pydantic's), `like_pattern.py` (`contains_pattern`, `LIKE_ESCAPE`: the escaped contains-pattern of `GET /jobs?q=` and `GET /search`, phase 7b) and `platform_rules.py` (field checks shared by `PATCH /platforms/{id}` and `POST /platforms/setup`; each refusal is a fixed code such as `invalid_schedule_times`, `schedule_incomplete`, `invalid_name`, `invalid_url_pattern`).
* `server/database/` — Database interface: `core.py` (SQLAlchemy models and Pydantic schemas) and Alembic migrations under `migrations/`.
* `server/routers/` — FastAPI endpoints:
  - `auth.py`: JWT login, refresh, logout (invalidates token version `tv`); the session cookies are set by `_set_access_cookie` / `_set_refresh_cookie`. `POST /auth/change-password` (5/min per account, `CHANGE_PASSWORD_RATE` with `user_or_ip_key`) checks the current password (400, `tv` unchanged), then stores the new hash, increments `tv` (every other access and refresh token is revoked, as on logout) and answers with both cookies re-issued for the new `tv`, so the calling tab stays signed in. A new password (change-password; `POST /users`) is `NewPassword`: 8-128 characters (code points) and at most 72 UTF-8 bytes, because bcrypt reads only 72 bytes (422 on the field, the value never echoed); the web mirrors it in `PASSWORD_LIMITS` (`api/settingsPaths.ts`) and shows one fixed text for both upper bounds. `DELETE /user/reset` ("Alles zurücksetzen") takes the password in the JSON body (`FactoryResetRequest`, never the query), is limited to 5/min per account (`RESET_RATE` with `user_or_ip_key`: both endpoints check the password, so a stolen session on rotating IPs gets no more guesses, and users behind one NAT do not share a bucket; login and refresh stay keyed by IP), answers 400 `Incorrect password` first, then 409 `Crawl running` while any crawl of the user is registered or a lock of one of their sources is held (`any_crawl_running`, fails open without Redis), else deletes through `services/user_data.delete_user_content` and answers the counts. **Tokens (phase 7b, R9):** the JWT `sub` is the user id as a string, never the username, so a reused username never revives a deleted user's tokens. Each token carries `type` access or refresh: REST, `/ws` and the rate-limit key accept only access tokens, `/auth/refresh` only refresh tokens. A token is accepted only with `exp` and an ASCII decimal `sub` of up to 18 digits; `core/auth.token_claims` and `user_from_token` are the one source for creating and reading tokens. Session tokens from before 7b are refused, so every user logs in again once after the deploy. **Users (admin, phase 7b):** `POST /users` takes a username of 3-50 characters from `[A-Za-z0-9._@-]` (stripped) and a `NewPassword`; a duplicate, checked case-insensitively and also when the unique index refuses the insert, answers 409 `username_taken`. Only members are created; there is no role change and no admin password reset (7b-Q2). `GET /users` is ordered by username and takes `skip` >= 0 and `limit` 1-200 (default 100; the web asks for 200 and shows a fixed "Liste gekürzt" hint when 200 rows come back). `DELETE /users/{id}` answers 404 for an unknown user, then 409 `cannot_delete_self`, 409 `cannot_delete_admin` and 409 `Crawl running` (the target's crawls, `any_crawl_running`, fail-open without Redis), else deletes through `services/user_data.delete_user` and answers `{status: "deleted"}`.
  - `jobs.py`: CRUD for job applications, notes, re-scoring, and package generation triggers. `GET /jobs` items carry `pre_generation_status` and `interview_prep_present` (bool, never the prep text). `DELETE /jobs/{id}` on an archived job hard-deletes the job plus its `job_status_history` and `job_documents` rows first (legacy on-disk files are not cleaned, R-17); an active job is archived with reason `USER`. `GET /jobs` items also carry `status_changed_at` (latest `job_status_history.changed_at`, ISO UTC or null; one grouped query per page) and `application_draft_present` (bool, never the draft text); `q` is a trimmed, literal contains-search on title and company (`%`, `_` and `\` are escaped, whitespace only = no filter); `company_domain=<domain>` (phase 7b) is an exact, owner-scoped filter, validated by the shared `CompanyDomain`, that combines with `is_archived`. `POST /jobs/{id}/documents` checks the declared type against an allow-list (415 `unsupported_type`, the type is never echoed), reads through `core/uploads.py` (`read_upload`, `MAX_UPLOAD_BYTES` 10 MiB, 413 `file_too_large`) and checks the magic bytes (`require_type`, 415) for every allowed type except `text/plain` (`_UNSIGNED_TYPES`: plain text has no signature). A failed store logs the exception type only. **Archive all** `DELETE /jobs?keep_favorites=&keep_applications=` (both default true) archives the caller's active jobs with reason `USER` and answers `{status:"archived", count}`: never SEEN placeholders, a legacy NULL status counts as OPEN, `keep_favorites` keeps favourites, `keep_applications` keeps every status after OPEN (plus GENERATING and FAILED). With `permanent=true` it hard-deletes the matching archived jobs through `services/user_data.delete_job_rows` (history and documents first). **Interview prep run state** (feedback 1, T1; migration `w5x6y7z8a9b0`): `jobs.interview_prep_started_at` (non-null = a prep runs) and `jobs.interview_prep_error` (fixed text, never shown by the UI). `POST /jobs/{id}/interview-prep[/regenerate]` stamps the start and clears the error (`core/interview_prep_state.start_prep`) and commits before queueing; the worker re-stamps at its start, success clears the stamp, any failure clears it and stores `GENERATION_FAILED_ERROR` (no automatic retry); both outcomes publish `interview_prep_ready`. `GET /jobs/{id}` exposes `interview_prep_running`, `interview_prep_started_at` (ISO UTC or null; Feedback 2 - T3, for the elapsed time) and `interview_prep_error`. **Posting details of an existing job** (Feedback 2 - T8; migration `d2e3f4a5b6c7`): `POST /jobs/{id}/posting-details` (10/min, owner-scoped; 409 when `description` is blank; `{status:"running"}` while a run exists) stamps `jobs.posting_details_started_at`, clears `posting_details_error` (`core/posting_details_state.py`), commits and queues `worker.extract_posting_details_task` (120/270 s). The worker re-stamps, asks the AI for contacts, recruiter and salary only (`get_posting_details_messages`, instructions shared with the analysis prompt), re-reads the row `FOR UPDATE` and runs `apply_posting_details` (empty fields only, provenance in `posting_extracted`); an empty result stores `NOTHING_NEW`, a failure `EXTRACTION_FAILED`; both end with `posting_details_ended {job_id, user_id}`. `GET /jobs/{id}` exposes `posting_details_running`, `_started_at`, `_error`. **Company research of a job** (feedback 1, T2; migration `x6y7z8a9b0c1`): `POST /jobs/{id}/company-research {company_domain: CompanyDomain|null, force_refresh}` (10/min, `COMPANY_RESEARCH_RATE`; 422 on `body.company_domain`) stores the typed domain on the job as is (null clears it), answers `{status:"exists", domain}` when a profile exists and no refresh is asked, else stamps `jobs.company_research_started_at` (clears `company_research_error`, `core/company_research_state.py`), commits and queues `worker.research_job_company_task` (soft/hard 720/870 s). The worker re-stamps; without a domain it asks the AI (`services/company_identification.py`, routed as `company_profile`) for the employer's domain from company name, title and posting URL, validated by the shared validator and refused when it is a known job-board or redirect host or a subdomain of one (`services/company_domain.JOB_BOARD_HOSTS`/`REDIRECT_HOSTS`, `is_job_board_or_redirect`; the employer's own posting or source host is accepted); none -> error `DOMAIN_NOT_FOUND`. The migration's data step cannot tell a user-confirmed domain equal to the posting host from a guess. It then builds the shared profile (skipped when one exists and no refresh), clears the stamp, and any failure stores `RESEARCH_FAILED`, except an AI connection error, which the identification and the profile call each retry once after 5 s (`_retry_dropped_connection`; a timeout is not retried) and which stores `AI_UNREACHABLE` when it persists (Feedback 2 - T1). No other automatic retry. Both outcomes publish `company_profile_ready {domain|null, job_id}`. `GET /jobs/{id}` exposes `company_research_running`, `company_research_started_at` (ISO UTC or null, Feedback 2 - T3) and `company_research_error` (fixed codes); since Feedback 2 - T3 it also exposes `generation_started_at` (ISO UTC, null while the job waits in the queue).
  - `platforms.py`: CRUD for platform targets, deferred crawl setup, pattern inference. `PATCH /platforms/{id}` validates `schedule_times` (1-6 unique HH:MM values 00:00-23:59, stored sorted; `[]` is a 422), `schedule_days` (unique 0-6, non-empty) and `name` (1-100 chars after trim). `url_pattern` is writable (1-300 chars, not only `/`). Time and days are set or cleared together: one half alone is a 422 `schedule_incomplete` on the missing field, so a schedule is cleared only with `schedule_times: null, schedule_days: null` in one request (`[]` is 422). A URL change keeps name and favicon and compares canonical hosts (`_site_of`). `POST /platforms/setup`, the legacy `POST /platforms/{id}/setup`, `POST /platforms/{id}/crawl` and the scraper's `POST /search` (also reached through the `/scraper/*` proxy) answer 409 `profile_required` while the user's profile is not complete (`core/profile_rules.py`, the rule behind `GET /setup-status` `profile_complete`: role and skills not blank); the scheduler skips such users (info log, no personal data). **URL pattern rule** (`core/platform_rules.url_matches_pattern`, used by `workers/tasks/urls.py` and mirrored by the web's `matchingCount`): a pattern starting with `/` must begin the link's path plus query (`startswith`); any other, older pattern stays a substring test on the whole URL. `_infer_url_pattern` yields path-plus-query prefixes. `POST /platforms/setup` accepts `name?` (no AI call when given), `schedule_times?`/`schedule_days?` and `url_pattern?` (no inference when given), and needs at least one `selected_urls`. `POST /platforms/url-pattern` (`{selected_urls}`, 1-1000 links of at most 2048 characters) answers `{url_pattern}` from the same `_infer_url_pattern` the setup uses, so the wizard shows and confirms the pattern before it is stored; it fetches and stores nothing. `GET /platforms` carries `favicon_url` (Google's favicon service, set on create; the web loads it with no referrer and falls back to a monogram). `POST /platforms/{id}/crawl` answers 200 `{status, job_id}`, 409 `Crawl already running` (scraper code `already_running`) or 502 for any other scraper refusal (fixed text). `last_crawl_at` is stamped only on an accepted start (`crawl_registry.is_started`, the one accept rule for the router, `_start_first_crawl` and the scheduler; the legacy `POST /platforms/{id}/setup` starts through `_start_first_crawl` too). Both preview proxies wait `PREVIEW_TIMEOUT_SECONDS` (`page_rendering.HTTP_TIMEOUT_SECONDS` + 2 x `DNS_TIMEOUT_SECONDS` + 5 s), longer than the scraper's two DNS checks plus one render call. `GET /platforms/{id}/runs` returns the run history (`limit` default 10, max 50; owner-scoped via `_owned_platform`). `DELETE /platforms/{id}` takes no query parameters. It deletes the source's SEEN placeholders and run history, detaches all other jobs (`platform_id = NULL`) and returns `{"status": "deleted", "kept_jobs": n}`, where n counts only the caller's jobs. It answers 409 `Crawl running` while the source's crawl lock is held or a crawl of it is registered. If Redis (result backend and crawl registry; the Celery broker is RabbitMQ) is unreachable, the delete proceeds (`_crawl_running` fails open): no new crawl can start without Redis, and on PostgreSQL the `job_entries.platform_id` foreign key rejects a late job insert that names the deleted platform. The legacy `GET /platforms/{id}/preview-links`, `POST /platforms/{id}/setup`, `POST /platforms/{id}/crawl` and the scheduler use the stored URL and rely on the scraper and worker re-checks. The channel test `POST /notifications/channels/{id}/test` is limited to 5/min per user (`NOTIFICATION_TEST_RATE`, `user_or_ip_key` in `routers/deps.py`: the signed-in user from a validly signed access token, else the client IP). `PATCH /platforms/{id}` bounds the per-source notification copies (`*_template` at most 100,000 characters, `""` stored as no template; `*_recipients` at most 50 addresses of the `EmailAddress` shape) only when the sent value differs from the stored one (`_checked_copy`), so a legacy value sent back unchanged by the drawer never refuses a save; a refusal is the request-validation 422 at `["body", field, ...]`.
  - `notifications.py` (T16): the user's channels, proxied to the notification service with the owner derived from the signed-in user. `GET /notifications/channel-types` -> `{items}`; `GET /notifications/channels` -> `{items, total}`; `POST /notifications/channels` `{type, name, fields}` -> 201 + `Location`; `GET`/`PATCH` (`{name?, fields?}`, null clears a field, an omitted secret stays)/`DELETE` (204; also drops the id from the user's sources) `/notifications/channels/{id}`; `POST /notifications/channels/{id}/test` (5/min per user) -> `{channel_id, delivered, reason}`. A channel answers `{id, type, name, fields, secrets, created_at, updated_at}` (no owner). Failures: 422 per field (`loc ["body", "fields", <name>]`), 404 `Channel not found` (also another user's channel), 409 `channel_limit_reached`, 429 with `Retry-After`, 502 `notification_service_unavailable`. `PATCH /platforms/{id}` takes `notification_channel_ids` (max 20 UUIDs of the user's channels, 422 `unknown channel` at the index otherwise); the platform answer carries `notification_channel_ids` and the derived `notification_adapters`.
  - `settings.py` / `admin.py`: Global configuration, Cloud/Local AI configs and notifications. `GET /matching-preference/distribution` -> `{counts: int[101]}` of the user's scored `OPEN` jobs that are active or `THRESHOLD`-archived (half-up buckets like the client; approximate vs the raw-float `match_score < threshold` of `/matching-preference/preview`). `GET /setup-status` -> `{has_source, ai_configured, profile_complete, has_jobs}` (booleans only, owner-scoped; `has_jobs` ignores `STATUS_SEEN` placeholders; `ai_configured` = `intelligence.service.is_ai_configured`, which follows the provider routing of the analysis task (`get_task_provider("job_analysis")`, default cloud) like `get_client_and_model`: routed `local` needs a DB or env Ollama URL (an unset URL is not configured although AI calls fall back to localhost), any other routing needs the DB OpenRouter key). Profile fields are bounded on `POST /settings` (limits in section 3). A template selection (`POST /settings`, `PATCH /settings/template`) that names a template still in the AI fill answers 409 `template_processing`. **CV import** `POST /settings/upload-cv` (10/min): a sync endpoint (FastAPI's threadpool, because the AI call blocks). **CV import run state** (Feedback 2 - T2; migration `c1d2e3f4a5b6`): `user_settings.cv_import_started_at` / `cv_import_error` (`core/cv_import_state.py`). After the upload checks (413/415/422 never start a run) the endpoint stamps and commits the start (409 `cv_import_running` while one runs), success clears the stamp in the store's commit, every failure clears it and stores `cv_parse_failed`; both outcomes publish `cv_import_ended {user_id}`. A browser reload does not end the request thread, so the stored CV still lands. `GET /settings` adds `cv_import_running`, `cv_import_started_at` (ISO UTC|null) and `cv_import_error`. It reads through `core/uploads.py` (`read_upload_sync`, 10 MiB) and requires `%PDF-` magic bytes whatever the name or declared type. The text is bounded to `CV_MAX_PAGES` 10 pages and `CV_MAX_TEXT_CHARS` 30,000 characters. The AI client is routed like the analysis (`get_client_and_model(SETUP_AI_TASK)`, `job_analysis`, the same routing as `is_ai_configured`) and called through `_call_openrouter` (AI status banner) with `CV_PARSE_MAX_TOKENS` 16,000 (reasoning models spend tokens before the answer). The answer is normalised and validated into `ParsedCv` (`_normalised`: nulls dropped; lists and objects where text belongs are turned into text by `_text`, recursively: object values and scalar lists joined with `, `, a list of objects one line per object, e.g. a `skills` list or grouped object, a `duration` object or an `education` list; an `experience` / `projects` entry answered as plain text becomes its `description` / `name`; numbers coerced to text; the profile limits apply). Only non-empty `role`, `skills`, `min_salary` and `location` replace the stored values. All-blank experience and project entries are dropped (`_cv_content`), and `cv_data` is replaced as a whole only when the answer carries CV content (an entry or a non-empty `education`), so a PDF that is not a CV keeps the stored CV. Answers: 413 `file_too_large`, 415 `unsupported_type`, 422 `[{loc:["body","file"], msg:"cv_no_text"}]` (under 50 characters of text), 502 `cv_parse_failed` (AI error, wrong shape, empty choices, over-limit answer), 200 `{status, data:{role, skills, min_salary, location, cv_data}}` with the stored values. A parse failure is logged without CV content. **Notification contract (service, T16/T17):** channels and their secrets live only in the notification service; the server never stores or returns a credential. `/notifications/*` (`routers/notifications.py`) proxies the service with the owner derived from the signed-in user: `GET /notifications/channel-types`, `GET`/`POST /notifications/channels`, `GET`/`PATCH`/`DELETE /notifications/channels/{id}`, `POST /notifications/channels/{id}/test` (5/min per user). The field bounds are the service's (its schema comes from `GET /notifications/channel-types`); secrets are write-only (the service answers booleans, an omitted secret on PATCH stays, `null` clears a field, `""` is refused). `POST /settings` no longer carries notification fields and `GET /settings` leaves the old credential columns out. `POST /notification-templates/preview` (30/min per user) renders `{type, content}` with the fixed `_FakeJob` through the senders' own functions and sends nothing: `{html: true, body}` for the email types (user-authored HTML, untrusted) or `{html: false, body}` for Pushover. Template CRUD: name trimmed 1-100, content 1-100,000 characters; own templates under `/notification-templates`, global ones (`is_admin`) under `/admin/notification-templates`. `DELETE /settings` ("Profil zurücksetzen") empties Ziel and Lebenslauf (`_clear_goal_and_cv`: role, skills, salary, location, preferences, job URLs, languages, `cv_data`; no demo values) and keeps channels, templates and proofs; 404 without a profile row.
  - `admin.py` (phase 7b; every route depends on `get_current_admin_user`, 403 for a member, and no route answers 401 for a domain refusal): `GET/POST /admin/settings` share one answer, `_settings_answer` (routing merged over `TASK_DEFAULTS`, the key only as `openrouter_api_key_set`, `ollama_base_url_from_env` true when the env `OLLAMA_BASE_URL` is non-empty and never the value; POST adds `status`). Fields are bounded with 422 on the field: model 1-200, key at most 500 (`""` removes it), base URL empty or http(s) with a host, no userinfo and no link-local literal (169.254/16, fe80::/10, also in numeric forms), at most 500; routing keys must be `TASK_DEFAULTS` keys and values `cloud`/`local`. `POST /admin/test/openrouter|ollama` always answer 200: `{ok:true, model[, model_found, available_models]}` or `{ok:false, reason}`, with `reason` one of `auth|not_found|unreachable|timeout|failed|no_key|no_model|no_url`; `available_models` keeps string ids of 1-200 characters, at most `MAX_AVAILABLE_MODELS` (200), and `model_found` is computed over the full list before the cap. `GET /admin/openrouter/models` answers 400 `no_key`, or 502 `openrouter_failed` for any upstream failure, and never forwards the upstream status. The two tests and the model list are limited to 10/min (`ADMIN_TEST_RATE`). `GET /admin/system-status` -> `{ai_error}` with `auth|rate_limit|model_not_found|connection|server|unknown` or null (503 `status_unavailable` on a Redis outage); `DELETE /admin/clear-ai-error` deletes both Redis keys; `POST /admin/redis/cleanup` -> `{removed}` (stalled runs). `POST /admin/database/wipe` checks the admin's password (400 `wrong_password`, never 401) and is limited to `PASSWORD_CHECK_RATE` (5/min); the own scope deletes everything the admin owns except the account (`delete_user_content`: jobs, sources, proofs, own CV and notification templates, the profile row) and the company profiles no job refers to; `wipe_all_users` does the same for every account, then every remaining job, source, run and company profile (only the accounts and the admin templates with `user_id` NULL stay). The own scope goes through `services/user_data.delete_user_content`, so other accounts' jobs on the admin's sources are detached and kept; its profile step leaves jobs without a domain out of the `NOT IN` list (a NULL there would keep every profile). Both scopes answer 409 `Crawl running` while a crawl of an affected source owner runs (the own scope: the admin; all: every user who owns a source), through `routers/deps.refuse_while_crawling`, which `/user/reset` and `DELETE /users/{id}` share. `PATCH /admin/companies/{domain} {name}` (1-200 after the trim) -> `{domain, name}` keeps the domain key, and a later research keeps the stored name (`_shared_company_name`); `DELETE /admin/companies/{domain}` -> `{status: "deleted"}` removes only the shared profile (jobs keep their `company_domain`). Both answer 404 `Company profile not found` without a profile and are logged at INFO with the admin id and the domain. A delete while research for that domain is running (the task retries for about 60 s) may recreate the profile: the delete is not a lock. Every limit here uses `user_or_ip_key`.

* `server/services/` — Internal business logic:
  - `template_filler.py`: DOM-based slots filler (`data-slot` / `data-repeat` replacements) and the **CV template sandbox** (security-critical). User CV templates (and the AI annotation of an upload) are untrusted Jinja2 code: `render_jinja2_template` renders them in `jinja2.sandbox.ImmutableSandboxedEnvironment` with `autoescape=True` (CV values are AI output and must not inject markup; the bundled templates escape the same way). Any `TemplateError` (incl. `SecurityError` for private attributes such as `__globals__`, or mutating methods) is logged at ERROR and raised as `TemplateRejected` with the fixed message `TEMPLATE_REJECTED_MESSAGE`, which the package task stores as `generation_error`. Any other exception while rendering (ZeroDivisionError, RecursionError, TypeError, ...) is treated the same. The render itself runs in a short-lived child process (`sys.executable -m services.template_render_child`, JSON over stdin/stdout, minimal environment without application secrets, `RLIMIT_AS` `TEMPLATE_RENDER_MEMORY_BYTES` 512 MB, `RLIMIT_CPU` 15 s, wall-clock `TEMPLATE_RENDER_TIMEOUT_SECONDS` 20 s enforced by the parent which kills the child, stdout read capped); any child failure (exit code, timeout, oversize) is a `TemplateRejected`. The child is a resource boundary only (same uid, not a privilege boundary); the in-process sandbox is the security layer, and every server process (`core/celery_config.py`, `core/scraper_celery_config.py`, `main.py`, which also covers `scraper_api.py` and `workers/scraper_worker.py`) calls `prctl(PR_SET_DUMPABLE, 0)` at import (`core/process_hardening.py`, Linux only; prefork children inherit it) so the child cannot read the worker's `/proc/<pid>/environ`. It limits filters the sandbox cannot intercept (`center`, `format`, `join`, `replace`, macro/`~` doubling). `render_jinja2_in_process` is the first layer inside the child. The package task does not use a `with ThreadPoolExecutor` (its exit would wait for stuck workers and swallow the soft limit); it calls `shutdown(wait=False, cancel_futures=True)`. Inside the child the sandbox is `_BoundedSandboxedEnvironment`: `*` and `**` results above `MAX_TEMPLATE_VALUE_LENGTH` / `MAX_POWER_RESULT_BITS` raise, and rendering goes through `generate()` with the output capped at `MAX_RENDERED_HTML_LENGTH` (1,000,000 chars). At save time `validate_template` (POST/PUT `/document-templates`) runs `check_jinja2_template` on the sanitised HTML for CV templates only (cover letters are never Jinja-rendered, so a literal `{{` is legal) and `fill_cv_template_task` runs it on the AI-annotated result (on rejection the original stays, template status `annotation_rejected`): a parse error or a literal `_`-prefixed attribute/key/`attr()` name is a 422 `{"detail":[{"loc":["body","html"],...}]}`. The check is best-effort and easy to bypass (`'_'*2~'init'`, `map(attribute='__init__')`) and is deliberately not extended; the sandbox is the boundary. The hard limit of every AI-calling task is soft + `SOFT_LIMIT_AI_GRACE_SECONDS` (`AI_REQUEST_TIMEOUT_SECONDS` 120 s + `AI_RETRY_BACKOFF_MARGIN_SECONDS` 30 s = 150 s), because the OpenAI SDK catches `SoftTimeLimitExceeded` inside its retry loop and retries the request once, so a closer hard limit would kill the worker before it records the failure; 810 s stays below RabbitMQ's 1800 s default `consumer_timeout`. A soft-limit hit becomes the fixed `generation_error` `GENERATION_TIMEOUT_ERROR`; a hard kill is recovered by the beat task `ai.fail_stuck_generations` (`workers/tasks/generation_sweep.py`, every 60 s): jobs GENERATING longer than hard limit + `GENERATION_SWEEP_MARGIN_SECONDS` (120 s) according to `jobs.generation_started_at` (migration `u3v4w5x6y7z8`; stamped by the worker at task start via `mark_generation_running` (a conditional UPDATE `WHERE status='GENERATING'`, so a stale copy cannot stamp a cancelled job; `start_generation` resets it to null), never by the router, so queue waiting time never counts; cleared by `finish_generation`) are finished via `fail_generation` (restores an advanced `pre_generation_status`); rows without a stamp are not swept; the same beat task ends the other runs (see **Durable run state**); and every other generation failure stores the fixed `GENERATION_FAILED_ERROR` (only `TemplateRejected` text passes through). `document_renderer.py` keeps a plain `Environment` because it only loads the bundled files in `server/templates/`.

The external render service loads a job-board URL in a browser and returns the rendered page HTML; it is not a PDF renderer and no application HTML is ever sent to it. `base.py` defines the `PageRenderer` `typing.Protocol` (`fetch_html(self, url) -> str | None`: rendered HTML, or None on any failure; never raises). `page_render_service.py` holds `PageRenderServiceRenderer`, the adapter for `doublelayer/page-render-service` (compose service `ai-job-agent-page-render`). `__init__.py` is the only surface callers (`workers/scraper_worker.py`, `routers/platforms.py`) import: `get_page_renderer()` picks the adapter by `RENDER_SERVICE` (default `page-render-service`) from a name -> class registry (an unknown name raises `ValueError` listing the allowed names; cached per process), `fetch_html(url)` delegates to it, and `HTTP_TIMEOUT_SECONDS` (`RENDER_API_HTTP_TIMEOUT`, default 90) is the longest one render call may block, which the preview timeout in `routers/platforms.py` builds on. A new render service is a new adapter registered there; nothing outside the package names the concrete service. The adapter posts `{"url": url, "timeout": 45}` to `RENDER_API_URL` (full endpoint, code default `http://localhost:18431/api/v1/render`, the host port compose publishes on loopback for local development, compose default `http://ai-job-agent-page-render:8000/api/v1/render`) with `RENDER_API_KEY` as `Authorization: Bearer`; compose passes the same key to the service as `API_KEYS` (at least 32 characters; the service refuses to start without it). Timeouts: 45 s is the render budget (`RENDER_PAGE_TIMEOUT_SECONDS`); the service's queue wait (per-host slot and free browser, up to 20 s each) is not part of it, so 45 s + 40 s stays below the 90 s HTTP timeout and a queued render is not cut off client-side. 200 returns the body; any other status is None and logged at WARNING with the host only (`core.url_safety.host_for_log`), the HTTP status and the error envelope's `code` and `traceId`, never its `message`, the full URL, path or query; transport errors are logged by host and exception type only. No retries (also not on 429 `SERVICE_BUSY`). The service enforces its own SSRF egress guard (an egress proxy that blocks private and reserved targets, also after redirects, for sub-resources and against DNS rebinding) unless it runs with `ALLOW_PRIVATE_TARGETS=true`, which must stay off outside local development.

**Connection-test errors.** Channel tests (`POST /notifications/channels/{id}/test`, T17 removed the old per-type test routes) answer 200 with `delivered` and a fixed `reason`; the admin AI tests (`/admin/test/openrouter`, `/admin/test/ollama`) answer 200 with a fixed `reason` code instead (phase 7b, see `admin.py`), and none returns raw exception text (it is only logged with its stack trace). `core/connection_errors.py` maps exception types (openai, requests, httpx, smtplib, socket) and HTTP status codes to one fixed message: "Anmeldung abgelehnt (API-Schlüssel prüfen)" (401/403, auth errors), "Modell nicht gefunden" (404), "Server nicht erreichbar" (connection/DNS), "Zeitüberschreitung" (timeouts), else "Verbindungstest fehlgeschlagen". `reason_for_error` / `reason_for_status` are the one classifier: the admin test reasons come from them, and `message_for_error` / `message_for_status` map those reasons to the fixed messages through one table. Notification tests do not use this module; their service failures are the fixed answers of `routers/notifications.py` (`http_error`: 502 `notification_service_unavailable`, 429, ...). The API exposes `Content-Disposition` via CORS so the web client can read download filenames.

## 3. Database Schema Overview
From [core.py](/server/database/core.py):
* `users` — Authentication credentials, role settings, and session tracking (`token_version`).
* `jobs` — Crawled postings, matching scores/reasoning, and editable `cv_html` / `cover_letter_html` blocks (the single source of truth for PDF rendering). Lifecycle: `status` (changed by users only through `POST /jobs/{id}/status`), `is_archived` + `archive_reason` (`THRESHOLD` | `USER`), `kept_by_user` (shields a restored job from threshold runs), `pre_generation_status` (the status a running CV/letter generation started from, cleared when it ends; migration `s1t2u3v4w5x6`), `interview_at` (timezone-aware, nullable; migration `t2u3v4w5x6y7`). `PATCH /jobs/{id}` clears `next_follow_up_at` / `interview_at` on an explicit `null` and leaves them unchanged when omitted. Its `contact_persons` (max 20 of `name/role/email/phone`), `recruiter_info` (`name/role/email/phone`) and `salary_benchmark` (`min/max` 0..10,000,000, `max` not below `min` (422 located on `salary_benchmark.max`), `note`) are typed models that forbid unknown keys; `notes` max 20,000, `application_draft`/`cv_draft` max 50,000 chars. `PUT /jobs/{id}/documents/html` accepts at most 1,000,000 chars of HTML (`MAX_DOCUMENT_HTML_LENGTH`, same as the web client's `MAX_HTML_LENGTH`); `POST /jobs/{id}/generate` `improvement_notes` max 50,000 chars. The job analysis (`ai.analyze_job`) also reads contact persons, recruiter and salary range from the posting (`intelligence/posting_details.py`): the LLM output is validated with those same models (invalid parts dropped, never failing the analysis), written only into empty fields, and `posting_extracted` (JSON list of field names; migration `z8a9b0c1d2e3`) records which came from the posting until the user saves that field via PATCH. Job page data: `checklist` (`posting_opened`, `documents_checked`, `sent`), `todos` (max 50 `{id, text, done}`). Offer outcome (feedback 1 T14, migration `a9b0c1d2e3f4`): `outcome_notes` (text, max 20,000, shared by both outcome tabs), `first_day_checklist` (JSON with exactly `contract_signed`, `papers_ready`, `others_declined`, `route_planned`, `first_day_contact`, replaced as a whole), `start_date` (SQL `DATE`, a calendar day sent as `YYYY-MM-DD`, cleared by an explicit `null` like the other dates).
* `user_settings` — User preferences, CV data JSON, the legacy notification credentials (SMTP, Pushover, Resend, Mailjet; read-only since T16: only the one-off migration reads them, `notification_channels_migrated` marks a migrated profile so a channel deleted later is never re-created; dropping the columns is a follow-up), `email_global_recipient`. Profile field limits (`MAX_*` in `database/core.py`, mirrored by the web in `src/api/profilePaths.ts` `PROFILE_LIMITS`): `role` 200, `skills` 2000, `min_salary` 50, `location` 200, `preferences` 5000; `spoken_languages` at most 20 items of up to 50 characters; `cv_data.experience` and `cv_data.projects` at most 30 entries each (`MAX_CV_ENTRIES`), entry title fields (incl. `tech_stack`) 200, `duration` 100, `description` 5000, `education` 5000. Entry fields default to "" and accept numbers as text. A value over its limit answers 422 with `loc ["body", field, ...]`, and the input is never echoed. The server column defaults (`role` "Software Engineer", `skills` "Python, Docker", `location` "Remote", `min_salary` "60000") count as no content for the web's import confirm.
* `system_settings` — Global default models and API endpoints/keys for OpenRouter and Ollama.
* `job_platforms` — Registered sites, cron schedules, matching URL patterns, the notified channels `notification_channels` (`[{id, type}]` of notification-service channels, T16; the type is immutable in the service and kept for lists; the legacy `notification_adapters` switch list is only read by the migration) with per-type template copies and recipient lists, and `last_run` (`{started_at, finished_at, found, new, matched, error?}` of the latest finished crawl; `error` is one of `cancelled`, `unreachable`, `failed`; the first terminal summary per crawl wins; `seeded` is true for a seed run).
* `platform_runs` — Crawl history per platform (migration `v4w5x6y7z8a9`, revises `u3v4w5x6y7z8`): `platform_id` (FK to `job_platforms.id` with `ON DELETE CASCADE`, because account delete and the admin wipe delete platforms in bulk, bypassing the ORM; indexed), `started_at`, `finished_at`, `found`, `new`, `matched`, `seeded`, `error` (a fixed code). Written next to `last_run` by `workers/tasks/platform_runs.py`, which keeps the newest `RUN_HISTORY_LIMIT` (20) rows per platform with one DELETE statement. Read by `GET /platforms/{id}/runs`. A dev DB that ran `alembic upgrade head` on the pre-CASCADE version of this migration must be recreated, or the FK altered by hand.
* `document_templates` — Raw HTML layouts for resumes and cover letters (seeded with "Classic" structures). `html` is capped at `MAX_TEMPLATE_HTML_LENGTH` (1,000,000 chars, 422) on POST/PUT `/document-templates`; `name` is trimmed, 1-100 chars (`MAX_TEMPLATE_NAME_LENGTH`). `status`: `processing`, None (ready), `annotation_rejected`, `annotation_failed` (lifecycle under `workers/tasks/fill_cv_template.py` in section 2). `user_settings.cv_template` / `cover_letter_template` hold either a file template key (`classic`) or a template id (1-9 ASCII digits; other purely numeric values are rejected with 422); an id must belong to the user or be an admin template (settings endpoints answer 422 otherwise, workers fall back to the file template).
* `company_profiles` — Extracted tech stacks, salary benchmarks, and cultural summaries for domains.
* `company_deep_dives` — One row per user, company domain and focus text (`focus_hash` = sha256; unique `(user_id, domain, focus_hash)`; migration `c1d2e3f4a5b6`): run state (`started_at`, `error`) and the last `result` of a deep dive; never part of the shared `company_profiles`.
* `job_documents` — File attachments linked to a job (kind: `UPLOADED`, `GENERATED_CV`, `GENERATED_LETTER`, `ATTACHED_CERT`, `ATTACHED_REFERENCE`). `GENERATED_*` rows are no longer written (T12); they remain for jobs generated before.
* `profile_documents` — General candidate certificates or references (types: `REFERENCE`, `CERTIFICATE`).
* `job_status_history` — State history tracking transitions (e.g. `OPEN` -> `DRAFTED` -> `APPLIED`).

## 4. Hard Security & Logic Invariants
1. **Async Execution:** Heavy tasks (scraping, LLM generation) must run inside Celery queues. HTTP endpoints must only enqueue tasks and return task IDs. Exceptions are the bounded renders a user waits for directly: the template preview and the PDF download (T12) render in a resource-limited child process inside the request, rate-limited per user.
2. **Tenant Isolation:** Every database query must query with explicit owner validation: `user_id == current_user.id`.
3. **Token Versioning:** Login sessions validate the token version (`tv`). Logout and a password change increment `tv` in the `users` table, which revokes every REST session at its next request and refuses every new WebSocket connection (a password change re-issues the caller's cookies with the new `tv`). `/ws` checks `tv` only at connect, so an already open WebSocket stays open until it disconnects. Since phase 7b the token `sub` is the user id and its `type` (access or refresh) is checked on REST, `/ws` and refresh (see `auth.py`).
4. **SSRF Guard (`core/url_safety.py`):** User URLs are fetched only when every resolved address is public. Internal Ollama connections are not user URLs. The admin's local model base URL (`ollama_base_url`) is the one user-supplied URL not guarded here: it is admin-only and points at a LAN or localhost model server by purpose; it must be http(s) with a host, no userinfo and no link-local literal (169.254/16, fe80::/10, also in numeric forms). The check is on the literal only: no DNS resolution and no redirect check (the connection test follows redirects), which the admin-trusted field accepts (R8b).
   - **Canonical URL:** every user URL is normalised once (`canonical_http_url`). The host may not contain `%`, `\`, control, format or space characters. ASCII is lowercased, and Unicode goes through UTS #46 non-transitional IDNA to its A-label (`idna`, pinned). Only LDH names or strict IP literals pass; a host whose last label is numeric is refused unless the whole host is a literal; `localhost` and `*.localhost` are refused; userinfo is refused. Only the canonical URL is stored (setup, `POST /platforms`, `PATCH`) and forwarded (scraper queue, worker render call), so the checked name is exactly the name the render browser resolves.
   - **Two layers:** Pydantic validators (`ensure_public_http_url`) check syntax and literal IPs only, never DNS, because they run on the event loop. Endpoints resolve: the sync endpoints (`POST /platforms`, `PATCH /platforms/{id}`, `POST /platforms/preview-links`, `POST /platforms/setup`) run in FastAPI's threadpool and answer 422 `loc ["body","url"]`, `msg url_not_public`. The scraper's async `/search` and `/import-job` call `public_http_url` through `run_in_threadpool` and answer `{status: "Error"}` with a fixed text; its sync `/preview-links` answers `{links: []}`. The worker (`_is_safe_url`) re-checks right before every render call.
   - **DNS:** lookups run in a per-process pool of 8 threads (rebuilt after fork). Each is bounded by `DNS_TIMEOUT_SECONDS` (3 s) and fails closed: a timeout or a resolver error refuses the URL, and one non-public record is enough to refuse. IPv6 transition forms (mapped, IPv4-compatible, NAT64, 6to4) are judged by their embedded IPv4. Any port is accepted on a public host.
   - **No echo:** neither 422 responses nor the scraper's refusal echo the URL. Guard logs and the logs of `fetch_links_task` and `scrape_job_detail_task` name the host only (`host_for_log`).
   - **Not covered here:** redirects, DNS rebinding and page sub-resources inside the render browser; the page render service blocks them with its own egress guard (see `page_rendering/` in section 2). See the Open Questions in `progress-tracker.md` for what is still to verify.
5. **No DB-Metadata creation:** Always use Alembic migrations to mutate schemas. The one exception is `database/schema.py` (`python -m database.schema` at container start, also called in `main.py`): it waits for Postgres, and an empty database gets `create_all` plus `alembic stamp head`, because the migration chain cannot build an empty database (early tables such as `system_settings` were never created by a migration). Every non-empty database gets `alembic upgrade head`.
6. **WebSocket Scoping:** Every user-related pub/sub event carries a top-level `user_id` (an int or an ASCII digit string; bools, floats and anything else are dropped) and is delivered only to that user's sockets. Only `ai_error` and `ai_error_cleared` (`GLOBAL_EVENT_TYPES` in `core/connection_manager.py`) go to everyone; any other event without `user_id` is dropped and logged. The `ai_error` event carries the stored text; the new web ignores its `message` and only invalidates `["system-status"]`.
7. **Status Transitions:** User status changes go only through `POST /jobs/{id}/status`, are validated against `core/job_status.py::ALLOWED_TRANSITIONS` and always write `job_status_history`. System states are set outside that table: the routers set `GENERATING` (`/generate`, `/generate-package`) and end it on `/cancel-generation`, the workers end it on completion or failure. Every start and end goes through `core/job_status.py` (`start_generation`, `finish_generation`, `status_after_generation`): the start stores the current status in `pre_generation_status`; completion restores an advanced status (`APPLIED`, `INTERVIEW`, `OFFER`, `ACCEPTED`, `REJECTED`), else `DRAFTED`; failure restores an advanced status and keeps `generation_error`, else `FAILED`; cancel restores the stored status, else `DRAFTED` with a letter draft or `OPEN`. A regeneration therefore never moves an application backwards.
8. **Shared company profile privacy:** `CompanyProfile` is stored once per domain and served to every user, so `worker.generate_company_profile` and its prompt take no user data (no CV, role, skills, languages) and no job text of any user: the inputs are the company name (the stored name if the profile exists, else the requester's own newest job's company capped at 200 chars, else the domain; a refresh never renames) and the domain. `suitable_for` / `not_suitable_for` are generic fit statements from company facts; deep dives are per request (`POST /companies/{domain}/deep-dive`), receive no profile and are never stored in it (their result is stored per user in `company_deep_dives`).
9. **Company domain:** `JobEntry.company_domain` and the `{domain}` of `/companies/{domain}/analyze|deep-dive` must be a normalised hostname (`services/company_domain.py::validate_company_domain`: lowercase, labels of 1-63 chars, at least one dot, no port/userinfo/IP, max 253, IDN as `xn--`; 422 otherwise). It is set only by the user (typed in the Firma tab) or by the AI identification of a job research; the posting host is never used (feedback 1 T2: a Google redirect link made it `google.com`).
10. **Deleting a source never deletes jobs:** `DELETE /platforms/{id}` detaches them (`platform_id = NULL`); only SEEN placeholders and the run history go.
11. **Notification credentials never leave the notification service:** the server stores none (T16); channels come back with secrets only as `"set"` / `"not set"`, `GET /settings` leaves the old credential columns out and masks every other secret, and test-send and 422 responses never echo secrets, recipients or URLs. Secrets are write-only in the web too: parsed into booleans, inputs start empty, only a typed value is sent, `null` clears. Every `/notifications/*` call is scoped by `owner_for(current_user.id)`.
12. **One crawl per source:** a second start of the same source is refused (`already_running`, 409) by the registry check plus the Redis `SET NX` lock; every crawl end releases the lock by token.
13. **Profile reads carry no secrets into the web:** the web's profile schema keeps only profile fields of `GET /settings`; it never parses, keeps or sends a notification field or secret.
14. **Template and preview HTML is untrusted:** the web shows it only in an `<iframe sandbox="">` (no `allow-scripts`, no `allow-same-origin`) through `srcdoc`, after `prepareForEditing` with the editor CSP (which also removes `<template>`, so no declarative shadow root can bring back links or SMIL); never `dangerouslySetInnerHTML`, never a top-level `src`.
15. **Uploads are refused by content:** profile documents, job documents and the CV import check the bytes (`core/uploads.py::require_type`), not the file name or declared type alone, and read at most limit + 1 bytes (`read_upload` / `read_upload_sync`). Job documents use the same reader and check; `text/plain` (job documents only) has no signature and is accepted by its declared type.
