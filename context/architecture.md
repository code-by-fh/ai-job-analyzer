# AI Job Agent - System Architecture

Factual and concise system architecture documentation for developers and AI agents.

## 1. Process Model & Stack
* **Container Orchestration:** A single container manages services via `supervisord` with the following active processes:
  1. `uvicorn` (Port 8080): Main FastAPI backend (`main.py`) serving REST endpoints, WebSockets (`/ws`), and JWT authentication. Its `RequestValidationError` handler keeps FastAPI's 422 shape `{"detail":[...]}` but drops each error's `input` and `ctx.error`, so a rejected body (e.g. a 1 MB template) is never echoed back.
  2. `scraper_api`: Internal FastAPI service (`scraper_api.py`, internal Port 8081) for validation and crawl control.
  3. `celery` (`ai_queue`): Processes AI assessment, document packaging, notifications, and runs the Celery Beat (`-B`) scheduler.
  4. `scraper_celery` (`scraper_queue`): Executes headless Playwright/BeautifulSoup4 crawls.
  5. `xvfb`, `x11vnc`, `novnc` (Port 6080): Virtual frame buffer and VNC interface for visual scraper monitoring.
* **Services Stack:**
  - **Database:** PostgreSQL 15 (SQLAlchemy 2.0 ORM, Alembic migrations).
  - **Message Broker & Task Queue:** RabbitMQ (Celery Broker; `CELERY_BROKER_URL` is `amqp://...` in both compose files. Both Celery apps read it from `core/celery_broker.py`, whose default when the variable is unset is the compose RabbitMQ `amqp://guest:guest@ai-job-agent-rabbitmq:5672//`, so the scraper app and the ai worker never split across brokers).
  - **Cache & Pub/Sub:** Redis (Celery result backend, WS messaging, crawl progress state, crawl deduplication, the crawl registry `user:{id}:active_crawls` and the per-source crawl lock `crawl_lock:{user}:{platform}`, and the stored AI error: the legacy text `system:ai_404_error` plus its code `system:ai_error_code`, phase 7b). Redis is not the Celery broker. The crawl Lua scripts assume single-node Redis.
  - **LLMs:** Cloud models via OpenRouter (job analysis, cover letter, research) and local models via Ollama (tailored CV generation). Client limits (`intelligence/service.py`): OpenRouter `AI_REQUEST_TIMEOUT_SECONDS` 120 s with `AI_MAX_RETRIES` 1, Ollama `OLLAMA_REQUEST_TIMEOUT_SECONDS` 600 s with `OLLAMA_MAX_RETRIES` 0. In both cases the worst case stays below the 900 s crawl stall threshold, which a test pins.
  - **Frontend:** `frontend/` (Next.js 16 App Router, React 19, Tailwind CSS v4, TanStack Query; no component libraries), compose service `ai-job-agent-frontend` on port 3000 (`ALLOWED_ORIGINS` default `http://localhost:3000`), built as a standalone server (`frontend/Dockerfile`, Node 22) whose API URL is injected at start by `frontend/env.sh`.

## 2. Directory Layout & Key Boundaries
* `server/core/` — Cross-cutting concerns: `auth.py` (JWT & Token Versioning), `connection_manager.py` (WebSockets), `celery_config.py`, `logger.py` and `job_status.py` (status transition table, archive/restore rules, the generation status rule and the `STATUS_SEEN` constant, shared by routers and workers), `url_safety.py` (SSRF guard, see section 4), `crawl_registry.py` (crawl registry, lock and heartbeat, see `workers/`; also `SCRAPER_START_TIMEOUT_SECONDS`, DNS bound + 2 s, the one wait for a scraper crawl start used by the API and the scheduler), `celery_broker.py` (the one `BROKER_URL` of both Celery apps), `uploads.py` (user uploads: `read_upload` / `read_upload_sync` read at most `max_bytes` + 1 bytes (default `MAX_UPLOAD_BYTES`, 10 MiB) and refuse more with 413 `file_too_large`; `require_type` checks the magic bytes against the declared or expected type (PDF, PNG, JPEG, WebP, DOC, DOCX) and refuses with 415 `unsupported_type`; the client's file name and declared type are never echoed; `content_disposition` builds every file download header of profile and job documents, an ASCII fallback plus RFC 5987 `filename*`, so a quote cannot break the header and a non-Latin-1 name cannot make Starlette raise; `field_error` shapes a fixed 422 item like pydantic's), `oauth_state.py` (the signed Drive OAuth `state`, see `storage.py` below), `like_pattern.py` (`contains_pattern`, `LIKE_ESCAPE`: the escaped contains-pattern of `GET /jobs?q=` and `GET /search`, phase 7b) and `platform_rules.py` (field checks shared by `PATCH /platforms/{id}` and `POST /platforms/setup`; each refusal is a fixed code such as `invalid_schedule_time`, `schedule_incomplete`, `invalid_name`, `invalid_url_pattern`).
* `server/database/` — Database interface: `core.py` (SQLAlchemy models and Pydantic schemas) and Alembic migrations under `migrations/`.
* `server/routers/` — FastAPI endpoints:
  - `auth.py`: JWT login, refresh, logout (invalidates token version `tv`); the session cookies are set by `_set_access_cookie` / `_set_refresh_cookie`. `POST /auth/change-password` (5/min per account, `CHANGE_PASSWORD_RATE` with `user_or_ip_key`) checks the current password (400, `tv` unchanged), then stores the new hash, increments `tv` (every other access and refresh token is revoked, as on logout) and answers with both cookies re-issued for the new `tv`, so the calling tab stays signed in. A new password (change-password; `POST /users`) is `NewPassword`: 8-128 characters (code points) and at most 72 UTF-8 bytes, because bcrypt reads only 72 bytes (422 on the field, the value never echoed); the web mirrors it in `PASSWORD_LIMITS` (`api/settingsPaths.ts`) and shows one fixed text for both upper bounds. `DELETE /user/reset` ("Alles zurücksetzen") takes the password in the JSON body (`FactoryResetRequest`, never the query), is limited to 5/min per account (`RESET_RATE` with `user_or_ip_key`: both endpoints check the password, so a stolen session on rotating IPs gets no more guesses, and users behind one NAT do not share a bucket; login and refresh stay keyed by IP), answers 400 `Incorrect password` first, then 409 `Crawl running` while any crawl of the user is registered or a lock of one of their sources is held (`any_crawl_running`, fails open without Redis), else deletes through `services/user_data.delete_user_content` and answers the counts. **Tokens (phase 7b, R9):** the JWT `sub` is the user id as a string, never the username, so a reused username never revives a deleted user's tokens. Each token carries `type` access or refresh: REST, `/ws` and the rate-limit key accept only access tokens, `/auth/refresh` only refresh tokens. A token is accepted only with `exp` and an ASCII decimal `sub` of up to 18 digits; `core/auth.token_claims` and `user_from_token` are the one source for creating and reading tokens. Session tokens from before 7b are refused, so every user logs in again once after the deploy. **Users (admin, phase 7b):** `POST /users` takes a username of 3-50 characters from `[A-Za-z0-9._@-]` (stripped) and a `NewPassword`; a duplicate, checked case-insensitively and also when the unique index refuses the insert, answers 409 `username_taken`. Only members are created; there is no role change and no admin password reset (7b-Q2). `GET /users` is ordered by username and takes `skip` >= 0 and `limit` 1-200 (default 100; the web asks for 200 and shows a fixed "Liste gekürzt" hint when 200 rows come back). `DELETE /users/{id}` answers 404 for an unknown user, then 409 `cannot_delete_self`, 409 `cannot_delete_admin` and 409 `Crawl running` (the target's crawls, `any_crawl_running`, fail-open without Redis), else deletes through `services/user_data.delete_user` and answers `{status: "deleted"}`.
  - `jobs.py`: CRUD for job applications, notes, re-scoring, and package generation triggers. `GET /jobs` items carry `pre_generation_status` and `interview_prep_present` (bool, never the prep text). `DELETE /jobs/{id}` on an archived job hard-deletes the job plus its `job_status_history` and `job_documents` rows first (legacy on-disk and Drive files are not cleaned, R-17); an active job is archived with reason `USER`. `GET /jobs` items also carry `status_changed_at` (latest `job_status_history.changed_at`, ISO UTC or null; one grouped query per page) and `application_draft_present` (bool, never the draft text); `q` is a trimmed, literal contains-search on title and company (`%`, `_` and `\` are escaped, whitespace only = no filter); `company_domain=<domain>` (phase 7b) is an exact, owner-scoped filter, validated by the shared `CompanyDomain`, that combines with `is_archived`. `POST /jobs/{id}/documents` checks the declared type against an allow-list (415 `unsupported_type`, the type is never echoed), reads through `core/uploads.py` (`read_upload`, `MAX_UPLOAD_BYTES` 10 MiB, 413 `file_too_large`) and checks the magic bytes (`require_type`, 415) for every allowed type except `text/plain` (`_UNSIGNED_TYPES`: plain text has no signature). A failed store logs the exception type only. **Archive all** `DELETE /jobs?keep_favorites=&keep_applications=` (both default true) archives the caller's active jobs with reason `USER` and answers `{status:"archived", count}`: never SEEN placeholders, a legacy NULL status counts as OPEN, `keep_favorites` keeps favourites, `keep_applications` keeps every status after OPEN (plus GENERATING and FAILED). With `permanent=true` it hard-deletes the matching archived jobs through `services/user_data.delete_job_rows` (history and documents first).
  - `platforms.py`: CRUD for platform targets, deferred crawl setup, pattern inference. `PATCH /platforms/{id}` validates `schedule_time` (HH:MM 00:00-23:59), `schedule_days` (unique 0-6, non-empty) and `name` (1-100 chars after trim). `url_pattern` is writable (1-300 chars, not only `/`). Time and days are set or cleared together: one half alone is a 422 `schedule_incomplete` on the missing field, so a schedule is cleared only with `schedule_time: null, schedule_days: null` in one request (`""` and `[]` are 422). A URL change keeps name and favicon and compares canonical hosts (`_site_of`). `POST /platforms/setup` accepts `name?` (no AI call when given), `schedule_time?`/`schedule_days?` and `url_pattern?` (no inference when given), and needs at least one `selected_urls`. `POST /platforms/{id}/crawl` answers 200 `{status, job_id}`, 409 `Crawl already running` (scraper code `already_running`) or 502 for any other scraper refusal (fixed text). `last_crawl_at` is stamped only on an accepted start (`crawl_registry.is_started`, the one accept rule for the router, `_start_first_crawl` and the scheduler; the legacy `POST /platforms/{id}/setup` starts through `_start_first_crawl` too). Both preview proxies wait `PREVIEW_TIMEOUT_SECONDS` (`render_client.HTTP_TIMEOUT_SECONDS` + 2 x `DNS_TIMEOUT_SECONDS` + 5 s), longer than the scraper's two DNS checks plus one render call. `GET /platforms/{id}/runs` returns the run history (`limit` default 10, max 50; owner-scoped via `_owned_platform`). `DELETE /platforms/{id}` takes no query parameters. It deletes the source's SEEN placeholders and run history, detaches all other jobs (`platform_id = NULL`) and returns `{"status": "deleted", "kept_jobs": n}`, where n counts only the caller's jobs. It answers 409 `Crawl running` while the source's crawl lock is held or a crawl of it is registered. If Redis (result backend and crawl registry; the Celery broker is RabbitMQ) is unreachable, the delete proceeds (`_crawl_running` fails open): no new crawl can start without Redis, and on PostgreSQL the `job_entries.platform_id` foreign key rejects a late job insert that names the deleted platform. The legacy `GET /platforms/{id}/preview-links`, `POST /platforms/{id}/setup`, `POST /platforms/{id}/crawl` and the scheduler use the stored URL and rely on the scraper and worker re-checks. The four `POST /platforms/{id}/test-*` are limited to 5/min per user (`NOTIFICATION_TEST_RATE`, `user_or_ip_key`). `PATCH /platforms/{id}` bounds the per-source notification copies (`*_template` at most 100,000 characters, `""` stored as no template; `*_recipients` at most 50 addresses of the `EmailAddress` shape) only when the sent value differs from the stored one (`_checked_copy`), so a legacy value sent back unchanged by the drawer never refuses a save; a refusal is the request-validation 422 at `["body", field, ...]`.
  - `settings.py` / `admin.py`: Global configuration, Cloud/Local AI configs, notifications, and storage credentials. `GET /matching-preference/distribution` -> `{counts: int[101]}` of the user's scored `OPEN` jobs that are active or `THRESHOLD`-archived (half-up buckets like the client; approximate vs the raw-float `match_score < threshold` of `/matching-preference/preview`). `GET /setup-status` -> `{has_source, ai_configured, profile_complete, has_jobs}` (booleans only, owner-scoped; `has_jobs` ignores `STATUS_SEEN` placeholders; `ai_configured` = `intelligence.service.is_ai_configured`, which follows the provider routing of the analysis task (`get_task_provider("job_analysis")`, default cloud) like `get_client_and_model`: routed `local` needs a DB or env Ollama URL (an unset URL is not configured although AI calls fall back to localhost), any other routing needs the DB OpenRouter key). `GET /notification-settings/channels` -> `{PUSHOVER, RESEND, MAILJET, SMTP}`, booleans only (`_channel_status`, the same credential predicates as the `/platforms/{id}/test-*` endpoints); no credential or address leaves the server. Profile fields are bounded on `POST /settings` (limits in section 3). A template selection (`POST /settings`, `PATCH /settings/template`) that names a template still in the AI fill answers 409 `template_processing`. **CV import** `POST /settings/upload-cv` (10/min): a sync endpoint (FastAPI's threadpool, because the AI call blocks). It reads through `core/uploads.py` (`read_upload_sync`, 10 MiB) and requires `%PDF-` magic bytes whatever the name or declared type. The text is bounded to `CV_MAX_PAGES` 10 pages and `CV_MAX_TEXT_CHARS` 30,000 characters. The AI client is routed like the analysis (`get_client_and_model(SETUP_AI_TASK)`, `job_analysis`, the same routing as `is_ai_configured`) and called through `_call_openrouter` (AI status banner) with `CV_PARSE_MAX_TOKENS` 16,000 (reasoning models spend tokens before the answer). The answer is normalised and validated into `ParsedCv` (`_normalised`: nulls dropped; lists and objects where text belongs are turned into text by `_text`, recursively: object values and scalar lists joined with `, `, a list of objects one line per object, e.g. a `skills` list or grouped object, a `duration` object or an `education` list; an `experience` / `projects` entry answered as plain text becomes its `description` / `name`; numbers coerced to text; the profile limits apply). Only non-empty `role`, `skills`, `min_salary` and `location` replace the stored values. All-blank experience and project entries are dropped (`_cv_content`), and `cv_data` is replaced as a whole only when the answer carries CV content (an entry or a non-empty `education`), so a PDF that is not a CV keeps the stored CV. Answers: 413 `file_too_large`, 415 `unsupported_type`, 422 `[{loc:["body","file"], msg:"cv_no_text"}]` (under 50 characters of text), 502 `cv_parse_failed` (AI error, wrong shape, empty choices, over-limit answer), 200 `{status, data:{role, skills, min_salary, location, cv_data}}` with the stored values. A parse failure is logged without CV content. **Notification contract (phase 7a):** `POST /notification-settings` and the notification keys of `POST /settings` share the bounded types of `database/core.py` (`EmailAddress` 254 characters of the shape `x@y.z`, `Credential` 1-500, `HostName` 1-253, `Port` 1-65535); `""` is refused, only `null` clears a field, and only the keys sent are written (a secret sent back as `__masked__` keeps its value). Secrets are write-only: `GET /settings` returns them as `__masked__` and `GET /notification-settings/channels` as booleans. Every channel test (`/notification-settings/test-*`) and the old `test-email` are limited to 5/min per user (`user_or_ip_key` in `routers/deps.py`: the signed-in user from a validly signed access token, else the client IP); `TestNotificationBody.recipient` is an address or `""` (the stored default); `test-email` (unused by the web) answers the fixed `{success: true}` or fixed texts, never the recipient. `POST /notification-templates/preview` (30/min per user) renders `{type, content}` with the fixed `_FakeJob` through the senders' own functions and sends nothing: `{html: true, body}` for the email types (user-authored HTML, untrusted) or `{html: false, body}` for Pushover. Template CRUD: name trimmed 1-100, content 1-100,000 characters; own templates under `/notification-templates`, global ones (`is_admin`) under `/admin/notification-templates`. `DELETE /settings` ("Profil zurücksetzen") empties Ziel and Lebenslauf (`_clear_goal_and_cv`: role, skills, salary, location, preferences, job URLs, languages, `cv_data`; no demo values) and keeps channels, templates and proofs; 404 without a profile row.
  - `admin.py` (phase 7b; every route depends on `get_current_admin_user`, 403 for a member, and no route answers 401 for a domain refusal): `GET/POST /admin/settings` share one answer, `_settings_answer` (routing merged over `TASK_DEFAULTS`, the key only as `openrouter_api_key_set`, `ollama_base_url_from_env` true when the env `OLLAMA_BASE_URL` is non-empty and never the value; POST adds `status`). Fields are bounded with 422 on the field: model 1-200, key at most 500 (`""` removes it), base URL empty or http(s) with a host, no userinfo and no link-local literal (169.254/16, fe80::/10, also in numeric forms), at most 500; routing keys must be `TASK_DEFAULTS` keys and values `cloud`/`local`. `POST /admin/test/openrouter|ollama` always answer 200: `{ok:true, model[, model_found, available_models]}` or `{ok:false, reason}`, with `reason` one of `auth|not_found|unreachable|timeout|failed|no_key|no_model|no_url`; `available_models` keeps string ids of 1-200 characters, at most `MAX_AVAILABLE_MODELS` (200), and `model_found` is computed over the full list before the cap. `GET /admin/openrouter/models` answers 400 `no_key`, or 502 `openrouter_failed` for any upstream failure, and never forwards the upstream status. The two tests and the model list are limited to 10/min (`ADMIN_TEST_RATE`). `GET /admin/system-status` -> `{ai_error}` with `auth|rate_limit|model_not_found|connection|server|unknown` or null (503 `status_unavailable` on a Redis outage); `DELETE /admin/clear-ai-error` deletes both Redis keys; `POST /admin/redis/cleanup` -> `{removed}` (stalled runs). `POST /admin/database/wipe` checks the admin's password (400 `wrong_password`, never 401) and is limited to `PASSWORD_CHECK_RATE` (5/min); the own scope deletes the admin's jobs and sources and the company profiles no job refers to, `wipe_all_users` every user's jobs, sources (with their runs) and company profiles (accounts, profile rows, proofs and templates stay). The own scope goes through `services/user_data.delete_owned_jobs` / `delete_owned_platforms`, so other accounts' jobs on the admin's sources are detached and kept; its profile step leaves jobs without a domain out of the `NOT IN` list (a NULL there would keep every profile). Both scopes answer 409 `Crawl running` while a crawl of an affected source owner runs (the own scope: the admin; all: every user who owns a source), through `routers/deps.refuse_while_crawling`, which `/user/reset` and `DELETE /users/{id}` share. `PATCH /admin/companies/{domain} {name}` (1-200 after the trim) -> `{domain, name}` keeps the domain key, and a later research keeps the stored name (`_shared_company_name`); `DELETE /admin/companies/{domain}` -> `{status: "deleted"}` removes only the shared profile (jobs keep their `company_domain`). Both answer 404 `Company profile not found` without a profile and are logged at INFO with the admin id and the domain. A delete while research for that domain is running (the task retries for about 60 s) may recreate the profile: the delete is not a lock. Every limit here uses `user_or_ip_key`.
  - `profile_documents.py`: `POST /profile/documents` checks `doc_type` (422 `invalid_doc_type` on `["body","doc_type"]`), the declared type against an allow-list (415 `unsupported_type`), then reads through `core/uploads.py` (`read_upload`, 10 MiB, 413 `file_too_large`) and checks the magic bytes (`require_type`, 415); `label` is at most 200 characters, the stored file name is cut to 255. `GET /profile/documents` items carry `downloadable` (`_is_downloadable`: a `db://` blob with content; false for Drive files), and view/download use the same rule (400 otherwise) and send `content_disposition`.
  - `templates.py`: template CRUD. A template `name` is trimmed and must be 1-100 characters (`TemplateName`, 422 on `["body","name"]`). `DELETE /document-templates/{id}` (own, non-admin templates only) resets a profile `cv_template` / `cover_letter_template` naming that id to None (the bundled default) in the same commit. `GET /document-templates/preview?doc_type=CV|COVER_LETTER&template=<id|file key>` returns `{"html"}` rendered with the caller's own profile and no AI call (`services/template_preview.py`); limit 20/min (`PREVIEW_RATE`, each CV preview spawns a render child); 404 `Template not found` for a foreign, unknown or wrong-type id or an unknown bundled key; 422 `{"detail":"template_rejected"}` when the static check, the sandbox or the letter slot filler refuses the template; 422 (pydantic) for a bad `doc_type` or a `template` over 64 characters. A template still in the AI fill may be previewed (it shows the unannotated HTML).
  - `companies.py`: the company directory and research. `GET /companies?scope=own|all` -> `{items: [{domain, name, has_profile, analyzed_at, job_count}]}` (`services/company_directory.company_summaries`): `own` (default) lists the domains of the caller's own non-`SEEN` jobs (empty domains skipped), with or without a profile, and `job_count` counts those jobs including archived ones; `scope=all` is admin-only (403 `Admins only`) and adds every profile. It never loads `raw_data`. The full profile stays at `GET /companies/{domain}` (phase 2). `POST /companies/{domain}/analyze` and `/deep-dive` are limited to 10/min per user (`COMPANY_RESEARCH_RATE`); a start answered "exists" still counts against it. `DeepDiveRequest` bounds `focus` and `how_to_proceed` to 2000, `company_name` to 200 and `title` to 300 characters, and `language` to `de|en`; the web clips to the same bounds by code points (`DEEP_DIVE_LIMITS`).
  - `search.py` (phase 7b): `GET /search?q=` reads `SearchQuery` (`q` is trimmed, then 2-200 characters; 422 at `["query","q"]`) and is limited to `SEARCH_RATE` (60/min per user). It answers `{jobs: [<= 8 {id, title, company, company_domain, status, is_archived}], companies: [<= 5 {domain, name}]}` over own data only, also for admins: non-`SEEN` jobs whose title or company contains `q` (active first, then newest; `%`, `_` and `\` match literally through `core/like_pattern.py`) and the user's own companies by name or domain (`search_companies`). Case folding is the database's ILIKE for jobs and Python `lower()` for companies, so the search does not treat ß and ss as equal.
  - `storage.py`: Speicherort. `GET /storage/status` -> `{available, connected, active, email}` (`available` = the server has Google client id and secret; `connected` = a refresh token is stored; `active` `NONE` | `GOOGLE_DRIVE`; the user's own Drive address only, never a token). `POST /storage/toggle` (400 for an unknown service or Drive without a token), `POST /storage/google/disconnect` (clears token and address, sets `NONE`; the grant at Google is not revoked). Drive OAuth: `GET /storage/google/login` signs a `state` (`core/oauth_state.py`: user id, nonce, expiry 10 minutes, HMAC-SHA256 with `SECRET_KEY` under its own context) and sets the nonce cookie `drive_oauth_nonce` (HttpOnly, SameSite=Lax, `Path=/`, Secure per `COOKIE_SECURE`, max-age 10 minutes). The unauthenticated callback accepts only a state this server signed, unexpired, for the nonce in the cookie. Every failure (unconfigured server at login, cancelled consent, bad or expired state, foreign browser, Google error or non-JSON answer, no email, DB error) redirects to `/settings?error=google_auth_failed`, success to `/settings?tab=storage&success=google_connected`; both clear the cookie, and no JSON or Google text reaches the tab.
  - `websocket.py`: Custom WS authentication and pub/sub routing. `job_skipped` (crawl path of `workers/tasks/analyze.py`) carries `existing_job_id: str|null`, the id of the user's own duplicate (null otherwise; omitted on the seed path, so clients treat it as optional).
* `server/workers/` — Asynchronous queues:
  - `worker.py`: Entrypoint for the AI/General Celery app (`ai_queue`).
  - `scraper_worker.py`: Entrypoint for the Crawling Celery app (`scraper_queue`). `crawl_job_started` carries `platform_id`. `fetch_links_task` checks the cancel marker before its first write (a missing hash counts as cancelled), so it never recreates a reaped crawl. Crawl errors sent to the user are fixed texts (`core/crawl_errors.py`, e.g. `URL_UNREACHABLE_MESSAGE`). An unreachable start page and a detail page that fails to download both end the crawl through `fail_crawl_job` with `UNREACHABLE_FAILURE` (`URL_UNREACHABLE_MESSAGE`), stored as run error `unreachable` (a single dead detail link fails the whole run; see the Open Questions in `progress-tracker.md`), and the log lines of `fetch_links_task` and `scrape_job_detail_task` name `host_for_log(url)` only.
  - **One crawl per source (crawl contract):** `scraper_api.py` `/search` claims the source before it queues anything. A registered crawl of the platform (`active_crawl_for_platform`) or a held lock (`acquire_crawl_lock`, Redis `SET crawl_lock:{user}:{platform} <crawl id> NX EX`) makes it answer `{"status": "Error", "code": "already_running"}`. The lock is released if `_init_crawl_job` or `apply_async` raises. `/crawl-status` items carry `platform_id`. The crawl hash and its lock share one TTL, `CRAWL_TTL_SECONDS` (3600 s). `touch_crawl_progress` (one Lua script, `PROGRESS_SCRIPT`) stamps `last_progress_at` and refreshes both TTLs on every progress step, and it is a no-op once the hash is gone. Every crawl end (completion, cancel, fail, unreachable, reaper, startup cleanup) goes through `record_platform_run`, which frees the lock by token via the Lua compare-and-delete `RELEASE_SCRIPT`, so a newer crawl's lock survives. `workers/crawl_control.py` (no import-time effects) holds `cleanup_crawl_job`, `fail_crawl_job`, `stop_crawl_tasks` (the cancel marker `crawl_job:{id}:cancelled` for 600 s plus revoke without terminate) and `reap_stalled_crawls`. Every crawl end publishes an event after its run is stored, because the web learns of crawl ends only from events: `crawl_completed`/`crawl_job_completed`, `crawl_job_cancelled`, and `crawl_job_failed` (`crawl_failed_event`, integer `user_id`) from `fail_crawl_job`, the reaper and the startup cleanup. Worker failures (`analyze.py` AI and internal errors, `urls.py` filter errors, `scraper_worker.py` fetch errors) call `fail_crawl_job` directly; the scraper's `/fail-crawl` needs a session cookie the workers do not have. `fail_crawl_job(r, job_id, user_id, failure)` takes a `CrawlFailure(message, run_error)`: the workers pass the named instances `AI_FAILURE`, `INTERNAL_FAILURE` (both stored as `failed`) and `UNREACHABLE_FAILURE` (`unreachable`), and `/fail-crawl` wraps the sent text as `CrawlFailure(text, ERROR_FAILED)`. It stores the run, sets the cancel marker, revokes the tasks, publishes, then deletes the hash. It leaves alone a crawl whose hash is gone (cancelled, failed, reaped or expired; a live hash always has a `status`) and a completed crawl (its hash stays until the TTL), so a late sibling error sends no `crawl_job_failed` after one of those ends. The reaper runs as beat task `ai.cleanup_stale_redis_jobs` every 60 s and behind `POST /admin/redis/cleanup`. It removes a crawl after `STALE_NO_PROGRESS_SECONDS` (900 s) without progress, or after `CRAWL_TTL_SECONDS` for a crawl still queued (status `starting`). It records a failed run, sets the cancel marker and revokes the crawl's tasks before deleting the hash, then publishes `crawl_job_failed`. Completed crawls are left to their TTL. The startup cleanup (`cleanup_stale_jobs`) runs in the scraper API's FastAPI lifespan, never at import (Celery workers import the module too). It records a failed run per orphaned crawl, which releases its lock by token, deletes no other lock and publishes `crawl_job_failed` per crawl. Scheduler (`workers/tasks/scheduling.py`): a slot is consumed when `last_crawl_at` or `last_run.finished_at` is at or after today's slot time (`_slot_consumed`). A refused scheduled start records a failed run (`record_failed_run`), so it is not retried every minute. `already_running` records nothing.

Template status lifecycle: `processing` (set by `POST /document-templates` for an uploaded CV template; the fill runs; the template cannot be selected, 409 `template_processing`), `None` (ready, annotated), `annotation_rejected` (the AI result failed `validate_template`, i.e. sanitising plus `check_jinja2_template`; the original HTML stays), `annotation_failed` (the AI call failed or timed out, or storing failed; the original stays). `intelligence/service.py::annotate_cv_template_with_jinja2` raises on any AI failure or empty answer, and the task owns the failure state, so a failed fill is never stored as finished. Variables belong only in text or quoted attribute values. * `server/services/` — Internal business logic:
  - `template_filler.py`: DOM-based slots filler (`data-slot` / `data-repeat` replacements) and the **CV template sandbox** (security-critical). User CV templates (and the AI annotation of an upload) are untrusted Jinja2 code: `render_jinja2_template` renders them in `jinja2.sandbox.ImmutableSandboxedEnvironment` with `autoescape=True` (CV values are AI output and must not inject markup; the bundled templates escape the same way). Any `TemplateError` (incl. `SecurityError` for private attributes such as `__globals__`, or mutating methods) is logged at ERROR and raised as `TemplateRejected` with the fixed message `TEMPLATE_REJECTED_MESSAGE`, which the package task stores as `generation_error`. Any other exception while rendering (ZeroDivisionError, RecursionError, TypeError, ...) is treated the same. The render itself runs in a short-lived child process (`sys.executable -m services.template_render_child`, JSON over stdin/stdout, minimal environment without application secrets, `RLIMIT_AS` `TEMPLATE_RENDER_MEMORY_BYTES` 512 MB, `RLIMIT_CPU` 15 s, wall-clock `TEMPLATE_RENDER_TIMEOUT_SECONDS` 20 s enforced by the parent which kills the child, stdout read capped); any child failure (exit code, timeout, oversize) is a `TemplateRejected`. The child is a resource boundary only (same uid, not a privilege boundary); the in-process sandbox is the security layer, and every server process (`core/celery_config.py`, `core/scraper_celery_config.py`, `main.py`, which also covers `scraper_api.py` and `workers/scraper_worker.py`) calls `prctl(PR_SET_DUMPABLE, 0)` at import (`core/process_hardening.py`, Linux only; prefork children inherit it) so the child cannot read the worker's `/proc/<pid>/environ`. It limits filters the sandbox cannot intercept (`center`, `format`, `join`, `replace`, macro/`~` doubling). `render_jinja2_in_process` is the first layer inside the child. The package task does not use a `with ThreadPoolExecutor` (its exit would wait for stuck workers and swallow the soft limit); it calls `shutdown(wait=False, cancel_futures=True)`. Inside the child the sandbox is `_BoundedSandboxedEnvironment`: `*` and `**` results above `MAX_TEMPLATE_VALUE_LENGTH` / `MAX_POWER_RESULT_BITS` raise, and rendering goes through `generate()` with the output capped at `MAX_RENDERED_HTML_LENGTH` (1,000,000 chars). At save time `validate_template` (POST/PUT `/document-templates`) runs `check_jinja2_template` on the sanitised HTML for CV templates only (cover letters are never Jinja-rendered, so a literal `{{` is legal) and `fill_cv_template_task` runs it on the AI-annotated result (on rejection the original stays, template status `annotation_rejected`): a parse error or a literal `_`-prefixed attribute/key/`attr()` name is a 422 `{"detail":[{"loc":["body","html"],...}]}`. The check is best-effort and easy to bypass (`'_'*2~'init'`, `map(attribute='__init__')`) and is deliberately not extended; the sandbox is the boundary. Time bound: `workers/tasks/time_limits.py` sets Celery soft/hard limits (render PDF 60/90 s; generation tasks 240/390 s and the CV template fill 660/810 s, because they include AI calls). The hard limit of every AI-calling task is soft + `SOFT_LIMIT_AI_GRACE_SECONDS` (`AI_REQUEST_TIMEOUT_SECONDS` 120 s + `AI_RETRY_BACKOFF_MARGIN_SECONDS` 30 s = 150 s), because the OpenAI SDK catches `SoftTimeLimitExceeded` inside its retry loop and retries the request once, so a closer hard limit would kill the worker before it records the failure; 810 s stays below RabbitMQ's 1800 s default `consumer_timeout`. A soft-limit hit becomes the fixed `generation_error` `GENERATION_TIMEOUT_ERROR`; a hard kill is recovered by the beat task `ai.fail_stuck_generations` (`workers/tasks/generation_sweep.py`, every 60 s): jobs GENERATING longer than hard limit + `GENERATION_SWEEP_MARGIN_SECONDS` (120 s) according to `jobs.generation_started_at` (migration `u3v4w5x6y7z8`; stamped by the worker at task start via `mark_generation_running` (a conditional UPDATE `WHERE status='GENERATING'`, so a stale copy cannot stamp a cancelled job; `start_generation` resets it to null), never by the router, so queue waiting time never counts; cleared by `finish_generation`) are finished via `fail_generation` (restores an advanced `pre_generation_status`); rows without a stamp are not swept; and every other generation failure stores the fixed `GENERATION_FAILED_ERROR` (only `TemplateRejected` text passes through). `document_renderer.py` keeps a plain `Environment` because it only loads the bundled files in `server/templates/`.

  - `template_preview.py`: the template preview (Profil > Vorlagen) through the generation's renderers, without AI: a stored user CV template first goes through the static `check_jinja2_template`, then the isolated Jinja2 child (sandbox); a user letter template through the slot filler (`_filled_letter`, an unfillable `data-repeat` becomes `TemplateRejected`, logged by exception type only); a bundled template through `document_renderer`. ## 3. Database Schema Overview
From [core.py](/server/database/core.py):
* `users` — Authentication credentials, role settings, and session tracking (`token_version`).
* `jobs` — Crawled postings, matching scores/reasoning, and editable `cv_html` / `cover_letter_html` blocks (the single source of truth for PDF rendering). Lifecycle: `status` (changed by users only through `POST /jobs/{id}/status`), `is_archived` + `archive_reason` (`THRESHOLD` | `USER`), `kept_by_user` (shields a restored job from threshold runs), `pre_generation_status` (the status a running CV/letter generation started from, cleared when it ends; migration `s1t2u3v4w5x6`), `interview_at` (timezone-aware, nullable; migration `t2u3v4w5x6y7`). `PATCH /jobs/{id}` clears `next_follow_up_at` / `interview_at` on an explicit `null` and leaves them unchanged when omitted. Its `contact_persons` (max 20 of `name/role/email/phone`), `recruiter_info` (`name/role/email/phone`) and `salary_benchmark` (`min/max` 0..10,000,000, `max` not below `min` (422 located on `salary_benchmark.max`), `note`) are typed models that forbid unknown keys; `notes` max 20,000, `application_draft`/`cv_draft` max 50,000 chars. `PUT /jobs/{id}/documents/html` accepts at most 1,000,000 chars of HTML (`MAX_DOCUMENT_HTML_LENGTH`, same as the web client's `MAX_HTML_LENGTH`); `POST /jobs/{id}/generate` `improvement_notes` max 50,000 chars. Job page data: `checklist` (`posting_opened`, `documents_checked`, `sent`), `todos` (max 50 `{id, text, done}`).
* `user_settings` — User preferences, CV data JSON, notification configurations (SMTP, Pushover, Resend, Mailjet), and active storage credentials. Profile field limits (`MAX_*` in `database/core.py`, mirrored by the web in `src/api/profilePaths.ts` `PROFILE_LIMITS`): `role` 200, `skills` 2000, `min_salary` 50, `location` 200, `preferences` 5000; `spoken_languages` at most 20 items of up to 50 characters; `cv_data.experience` and `cv_data.projects` at most 30 entries each (`MAX_CV_ENTRIES`), entry title fields (incl. `tech_stack`) 200, `duration` 100, `description` 5000, `education` 5000. Entry fields default to "" and accept numbers as text. A value over its limit answers 422 with `loc ["body", field, ...]`, and the input is never echoed. The server column defaults (`role` "Software Engineer", `skills` "Python, Docker", `location` "Remote", `min_salary` "60000") count as no content for the web's import confirm.
* `system_settings` — Global default models and API endpoints/keys for OpenRouter and Ollama.
* `job_platforms` — Registered sites, cron schedules, matching URL patterns, notification overrides, and `last_run` (`{started_at, finished_at, found, new, matched, error?}` of the latest finished crawl; `error` is one of `cancelled`, `unreachable`, `failed`; the first terminal summary per crawl wins; `seeded` is true for a seed run).
* `platform_runs` — Crawl history per platform (migration `v4w5x6y7z8a9`, revises `u3v4w5x6y7z8`): `platform_id` (FK to `job_platforms.id` with `ON DELETE CASCADE`, because account delete and the admin wipe delete platforms in bulk, bypassing the ORM; indexed), `started_at`, `finished_at`, `found`, `new`, `matched`, `seeded`, `error` (a fixed code). Written next to `last_run` by `workers/tasks/platform_runs.py`, which keeps the newest `RUN_HISTORY_LIMIT` (20) rows per platform with one DELETE statement. Read by `GET /platforms/{id}/runs`. A dev DB that ran `alembic upgrade head` on the pre-CASCADE version of this migration must be recreated, or the FK altered by hand.
* `document_templates` — Raw HTML layouts for resumes and cover letters (seeded with "Classic" structures). `html` is capped at `MAX_TEMPLATE_HTML_LENGTH` (1,000,000 chars, 422) on POST/PUT `/document-templates`; `name` is trimmed, 1-100 chars (`MAX_TEMPLATE_NAME_LENGTH`). `status`: `processing`, None (ready), `annotation_rejected`, `annotation_failed` (lifecycle under `workers/tasks/fill_cv_template.py` in section 2). `user_settings.cv_template` / `cover_letter_template` hold either a file template key (`classic`) or a template id (1-9 ASCII digits; other purely numeric values are rejected with 422); an id must belong to the user or be an admin template (settings endpoints answer 422 otherwise, workers fall back to the file template).
* `company_profiles` — Extracted tech stacks, salary benchmarks, and cultural summaries for domains.
* `job_documents` — File attachments linked to a job (kind: `UPLOADED`, `GENERATED_CV`, `GENERATED_LETTER`, `ATTACHED_CERT`, `ATTACHED_REFERENCE`).
* `profile_documents` — General candidate certificates or references (types: `REFERENCE`, `CERTIFICATE`).
* `job_status_history` — State history tracking transitions (e.g. `OPEN` -> `DRAFTED` -> `APPLIED`).

## 4. Hard Security & Logic Invariants
1. **Async Execution:** Heavy tasks (scraping, PDF generation, LLM generation) must run inside Celery queues. HTTP endpoints must only enqueue tasks and return task IDs.
2. **Tenant Isolation:** Every database query must query with explicit owner validation: `user_id == current_user.id`.
3. **Token Versioning:** Login sessions validate the token version (`tv`). Logout and a password change increment `tv` in the `users` table, which revokes every REST session at its next request and refuses every new WebSocket connection (a password change re-issues the caller's cookies with the new `tv`). `/ws` checks `tv` only at connect, so an already open WebSocket stays open until it disconnects. Since phase 7b the token `sub` is the user id and its `type` (access or refresh) is checked on REST, `/ws` and refresh (see `auth.py`).
4. **SSRF Guard (`core/url_safety.py`):** User URLs are fetched only when every resolved address is public. Internal Ollama connections are not user URLs. The admin's local model base URL (`ollama_base_url`) is the one user-supplied URL not guarded here: it is admin-only and points at a LAN or localhost model server by purpose; it must be http(s) with a host, no userinfo and no link-local literal (169.254/16, fe80::/10, also in numeric forms). The check is on the literal only: no DNS resolution and no redirect check (the connection test follows redirects), which the admin-trusted field accepts (R8b).
   - **Canonical URL:** every user URL is normalised once (`canonical_http_url`). The host may not contain `%`, `\`, control, format or space characters. ASCII is lowercased, and Unicode goes through UTS #46 non-transitional IDNA to its A-label (`idna`, pinned). Only LDH names or strict IP literals pass; a host whose last label is numeric is refused unless the whole host is a literal; `localhost` and `*.localhost` are refused; userinfo is refused. Only the canonical URL is stored (setup, `POST /platforms`, `PATCH`) and forwarded (scraper queue, worker render call), so the checked name is exactly the name the render browser resolves.
   - **Two layers:** Pydantic validators (`ensure_public_http_url`) check syntax and literal IPs only, never DNS, because they run on the event loop. Endpoints resolve: the sync endpoints (`POST /platforms`, `PATCH /platforms/{id}`, `POST /platforms/preview-links`, `POST /platforms/setup`) run in FastAPI's threadpool and answer 422 `loc ["body","url"]`, `msg url_not_public`. The scraper's async `/search` and `/import-job` call `public_http_url` through `run_in_threadpool` and answer `{status: "Error"}` with a fixed text; its sync `/preview-links` answers `{links: []}`. The worker (`_is_safe_url`) re-checks right before every render call.
   - **DNS:** lookups run in a per-process pool of 8 threads (rebuilt after fork). Each is bounded by `DNS_TIMEOUT_SECONDS` (3 s) and fails closed: a timeout or a resolver error refuses the URL, and one non-public record is enough to refuse. IPv6 transition forms (mapped, IPv4-compatible, NAT64, 6to4) are judged by their embedded IPv4. Any port is accepted on a public host.
   - **No echo:** neither 422 responses nor the scraper's refusal echo the URL. Guard logs and the logs of `fetch_links_task` and `scrape_job_detail_task` name the host only (`host_for_log`).
   - **Not covered here:** see the Open Questions in `progress-tracker.md` for the render-service residuals (redirects, DNS rebinding, page JavaScript).
5. **No DB-Metadata creation:** Always use Alembic migrations to mutate schemas. The one exception is `database/schema.py` (`python -m database.schema` at container start, also called in `main.py`): it waits for Postgres, and an empty database gets `create_all` plus `alembic stamp head`, because the migration chain cannot build an empty database (early tables such as `system_settings` were never created by a migration). Every non-empty database gets `alembic upgrade head`.
6. **WebSocket Scoping:** Every user-related pub/sub event carries a top-level `user_id` (an int or an ASCII digit string; bools, floats and anything else are dropped) and is delivered only to that user's sockets. Only `ai_error` and `ai_error_cleared` (`GLOBAL_EVENT_TYPES` in `core/connection_manager.py`) go to everyone; any other event without `user_id` is dropped and logged. The `ai_error` event carries the stored text; the new web ignores its `message` and only invalidates `["system-status"]`.
7. **Status Transitions:** User status changes go only through `POST /jobs/{id}/status`, are validated against `core/job_status.py::ALLOWED_TRANSITIONS` and always write `job_status_history`. System states are set outside that table: the routers set `GENERATING` (`/generate`, `/generate-package`) and end it on `/cancel-generation`, the workers end it on completion or failure. Every start and end goes through `core/job_status.py` (`start_generation`, `finish_generation`, `status_after_generation`): the start stores the current status in `pre_generation_status`; completion restores an advanced status (`APPLIED`, `INTERVIEW`, `OFFER`, `ACCEPTED`, `REJECTED`), else `DRAFTED`; failure restores an advanced status and keeps `generation_error`, else `FAILED`; cancel restores the stored status, else `DRAFTED` with a letter draft or `OPEN`. A regeneration therefore never moves an application backwards.
8. **Shared company profile privacy:** `CompanyProfile` is stored once per domain and served to every user, so `worker.generate_company_profile` and its prompt take no user data (no CV, role, skills, languages) and no job text of any user: the inputs are the company name (the stored name if the profile exists, else the requester's own newest job's company capped at 200 chars, else the domain; a refresh never renames) and the domain. `suitable_for` / `not_suitable_for` are generic fit statements from company facts; deep dives are per request (`POST /companies/{domain}/deep-dive`), receive no profile and are never stored.
9. **Company domain:** `JobEntry.company_domain` and the `{domain}` of `/companies/{domain}/analyze|deep-dive` must be a normalised hostname (`services/company_domain.py::validate_company_domain`: lowercase, labels of 1-63 chars, at least one dot, no port/userinfo/IP, max 253, IDN as `xn--`; 422 otherwise). The analyze tasks set it from the posting host (lowercase, no `www.`, no port) except when that host equals the host of any of the user's platforms (job boards).
10. **Deleting a source never deletes jobs:** `DELETE /platforms/{id}` detaches them (`platform_id = NULL`); only SEEN placeholders and the run history go.
11. **Notification credentials never leave the server:** channel status is booleans only (`GET /notification-settings/channels`), `GET /settings` masks every secret, and test-send and 422 responses never echo secrets, recipients or URLs. Secrets are write-only in the web too: parsed into booleans, inputs start empty, only a typed value is sent, `null` clears.
12. **One crawl per source:** a second start of the same source is refused (`already_running`, 409) by the registry check plus the Redis `SET NX` lock; every crawl end releases the lock by token.
13. **Profile reads carry no secrets into the web:** the web's profile schema keeps only profile fields of `GET /settings`; it never parses, keeps or sends a notification field or secret.
14. **Template and preview HTML is untrusted:** the web shows it only in an `<iframe sandbox="">` (no `allow-scripts`, no `allow-same-origin`) through `srcdoc`, after `prepareForEditing` with the editor CSP (which also removes `<template>`, so no declarative shadow root can bring back links or SMIL); never `dangerouslySetInnerHTML`, never a top-level `src`.
15. **Uploads are refused by content:** profile documents, job documents and the CV import check the bytes (`core/uploads.py::require_type`), not the file name or declared type alone, and read at most limit + 1 bytes (`read_upload` / `read_upload_sync`). Job documents use the same reader and check; `text/plain` (job documents only) has no signature and is accepted by its declared type.
